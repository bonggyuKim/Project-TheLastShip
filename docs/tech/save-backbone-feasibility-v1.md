## 1. 협의 `9` — 시뮬 상태 스냅샷/복원 (게이트)

### 1.1 이 경로는 가설이 아니다. 이미 돌고 있다

`LastShiftSimulation` 에 "런타임 상태 전체를 한 번에 읽고 다시 주입하는 경로" 를 **낼 수 있는가** 가
질문이었는데, 답은 **이미 나 있다** 이다. 멀티플레이가 같은 문제를 먼저 풀었기 때문이다 —
서버가 시뮬 전체를 읽어 한 덩어리로 보내고 클라이언트가 그걸 통째로 주입한다.

| 조각 | 자리 | 하는 일 |
|---|---|---|
| 상태 그릇 | `Assets/DoodleUp/Scripts/Runtime/LastShiftNetworkSnapshot.cs:6` | **평평한 구조체 `36`필드.** 배 상태 `9` · 구역 압력 `3` · 문 `3` · 해치 `2` · 도킹 타이머 · 판정 · 마스크 |
| 읽기 | `LastShiftNetworkSandbox.cs:115` `PublishSnapshot()` | 살아 있는 컨트롤러에서 그 `36`필드를 뽑는다 |
| 주입 | `LastShiftSandboxController.cs:491` `ApplyNetworkSnapshot()` | 받아서 컨트롤러에 도로 앉힌다 |
| 항해 진행 주입 | `LastShiftVoyage.cs:189` `ApplyNetworkState()` | 구간 회차·전이·래치·진행 여부 |
| 여력 원장 주입 | `LastShiftMaintenance.cs:253` `ApplyNetworkLedger()` / `:269` `ApplyNetworkPurchases()` | 잔액·기항 회차·구매 이력 |
| 배치물 표 | `LastShiftPlacedModules.cs:92` (`Register` / `Clear`) | 정적 등록부. 재조립의 입력 |

**세이브가 요구하는 것과 네트워크가 요구하는 것은 같은 모양이다** — "지금 상태 전부를 값으로 접어
다른 곳에서 되살린다". 다른 점은 목적지가 소켓이냐 파일이냐뿐이고, 그건 직렬화 계층의 문제이지
시뮬레이션의 문제가 아니다.

### 1.2 상태 기반이라 결정성이 필요 없다 — 가장 큰 이론적 반론이 성립하지 않는다

"구간 중간부터 복원" 에 흔히 따라오는 반론은 **재생(replay) 이 어긋난다** 는 것이다. 여기엔 해당하지 않는다.

`AdvanceMission(Time.deltaTime)`(`LastShiftSandboxController.cs:660`)은 **누적 스칼라를 직접 굴린다.**
도킹 진행도는 `state.ThrustDemand * deltaTime` 를 더할 뿐이고(`LastShiftRecovery.cs:780`), 열도
`state.EngineHeat + heatDelta * deltaTime` 이다(`:698`). **어디에도 "처음부터 다시 돌려서 여기까지 온다"
가 없다.** 누적값 자체가 상태다.

그래서 복원은 누적값을 그대로 써 넣으면 끝이고, **가변 `dt` 도 tick 정렬도 문제가 되지 않는다.**
저장 시점과 복원 시점의 프레임 길이가 달라도 다음 tick 부터 같은 식이 이어질 뿐이다.

### 1.3 그래서 새로 해야 하는 일 — 필드 확장과 플래그 하나

경로가 있다는 것이 **그대로 쓸 수 있다** 는 뜻은 아니다. 두 가지가 걸린다.

**(가) 주입 경로가 "나는 클라이언트다" 를 같이 켠다.**
`ApplyNetworkSnapshot` 은 마지막에 `usesReplicatedState = true` 를 세우고(`:525`), 그 플래그는
`UncontainedSystemMask` 를 **직접 계산하지 않고 받은 값을 쓰도록** 바꾼다(`:323`–`:324`).
세이브 복원은 반대다 — 주입한 뒤 **호스트가 계속 계산해야 한다.**
→ 주입과 "권위를 넘긴다" 를 분리한다. 인자 하나짜리 수정이고 새 계통이 아니다.

**(나) 스냅샷이 아직 안 나르는 상태가 있다.** 이게 이 일의 실제 분량이다.
네트워크는 이것들을 안 보내도 됐다 — 클라이언트는 표시만 하지 판정을 안 내기 때문이다.
**세이브는 판정을 이어서 내야 하므로 전부 필요하다.**

| 빠진 상태 | 자리 | 왜 필요한가 |
|---|---|---|
| 조종 홀드(추력·자세·잔여 `8`초) | `LastShiftSimulation.cs:382` `LastShiftControlHold` | 복원 직후 조종 입력이 되살아나는 시점이 달라진다 |
| 조향 지연 잔여 · 대기 중 조종 입력 | `LastShiftSandboxController.cs:39`–`:42` | 전력 부족 조향 지연이 리셋된다 |
| 열 보호 누적 시간 | `:53` | 판정 원인 줄이 "왜 추력이 낮았는가" 를 잃는다 |

| 냉각 밸브를 잡고 있는 승무원 | `LastShiftSandboxController.cs:86` | 잡은 채로 저장하면 복원 후 냉각이 끊긴다 |

| 승무원 수트 산소·사망 | `LastShiftCrewOxygen.cs:28`–`:33` | 주입 훅은 이미 있다(`:142` `ApplyReplicated`) |

**아이템 위치는 조항 `S-7` 덕에 싸다.** 속도를 복원하지 않아도 되므로 위치·회전만 쓰고 속도는 `0`
으로 둔다 — `LastShiftGrabbable.ApplyPhysicsState()`(`:266`)가 이미 물리 상태를 세우는 자리다.

### 1.4 [정정 `2026-08-09`] 저장 중에도 시뮬은 계속 돈다 — 난이도가 오르지 않는다

> **전제 변경(사용자 재확인).** 조항 `S-1a`("저장 = 종료, 이어서 하기는 P2")가 폐기됐다.
> 저장은 세션을 끝내지 않는다 — **스냅샷을 뜨는 동안에도 시뮬레이션이 계속 돌아야 하고 `P1` 범위다.**
> 아래는 그 전제로 다시 본 결과다.

**결론: 난이도가 오르지 않는다. 오히려 할 일이 줄어든다.** 논블로킹 캡처는 만들어야 하는 것이
아니라 **이미 그렇게 돌고 있다.**

#### (가) 이미 매초 네 번 그렇게 하고 있다

```
// LastShiftNetworkSandbox.cs:54
private void Update()
{
    if (!IsServer || Time.unscaledTime < nextSnapshotTime) return;
    nextSnapshotTime = Time.unscaledTime + 0.25f;   // 0.25초마다
    RecoverItemsOutsideSafetyBounds();
    PublishSnapshot();                              // 전체 상태 캡처
}
```

**서버는 시뮬을 한 번도 멈추지 않고 `0.25`초마다 전체 스냅샷을 뜬다.** 정지 → 캡처 → 재개가
아니라 그냥 도는 중에 뜬다. 요구사항이 곧 현행 동작이다.

#### (나) 찢어진 스냅샷(tearing)이 구조적으로 불가능하다

논블로킹 캡처의 진짜 위험은 성능이 아니라 **필드마다 다른 tick 의 값이 섞이는 것**이다.
여기선 일어날 수 없다:

- 캡처는 `PublishSnapshot()` 안의 **동기 값 대입 한 덩어리**다(`:129`–`:159`).
- 시뮬 진행도 `AdvanceMission(Time.deltaTime)` **동기 호출 하나**다(`LastShiftSandboxController.cs:660`).
- 둘 다 메인 스레드다. 그래서 캡처는 **tick `N` 직후이거나 tick `N-1` 직후이지, tick 중간일 수 없다.**

어느 쪽이든 **자기모순 없는 한 시점의 상태**다. 프레임 실행 순서를 고정하지 않아도 정합성이 깨지지
않는다(고정하면 "저장 시각" 이 명확해지는 이득은 있다 — `LateUpdate` 나 `DefaultExecutionOrder` 한 줄).

#### (다) 값 타입이라 저장한 뒤 계속 놀아도 파일이 안 흔들린다

이게 "저장하고 계속 플레이" 를 **공짜로** 만드는 성질이다.
`LastShiftNetworkSnapshot` 은 `float`·`bool`·`int`·`enum` 뿐이고 **`GameObject`·`Transform` 참조가
하나도 없다**(`LastShiftNetworkSnapshot.cs:6`–`:57`). 캡처가 곧 **복사**이므로, 캡처 이후의 플레이가
이미 뜬 스냅샷을 건드릴 방법이 없다.

> 만약 스냅샷이 참조를 들고 있었다면 이 요구는 어려웠을 것이다 — 쓰기가 끝나기 전에 플레이가
> 같은 객체를 바꾸는 **라이브 에일리어싱**이 되고, 그걸 막으려면 진짜로 시뮬을 세워야 한다.
> **값 타입 선택이 이 요구를 미리 해결해 두었다.**

#### (라) 실제로 느린 것은 캡처가 아니라 파일 쓰기다 — 그리고 그건 스레드로 뺄 수 있다

| 단계 | 비용 | 스레드 |
|---|---|---|
| 캡처(필드 복사 약 `60`개) | **마이크로초** | 메인 (원자적) |
| JSON 직렬화 | 밀리초 | **백그라운드 가능** |
| 디스크 쓰기 | 밀리초~수십, 변동 큼 | **백그라운드 가능** |

**메인 스레드에서 캡처만 하고, 평평한 구조체를 워커에 넘겨 직렬화·쓰기를 시킨다.**
Unity 객체 참조가 없다는 (다)의 성질이 이 오프스레드를 **합법으로** 만든다.

- **단서 하나.** §1.3 이 추가하라고 한 아이템 실제 좌표와 승무원 상태는 `Transform`·`Rigidbody`
  읽기라 **메인 스레드에서만** 읽을 수 있다. 그래서 그 읽기는 캡처 단계 안에 들어가야 한다
  — 평평한 `Vector3` 로 뽑고 나면 그 뒤는 전부 스레드 안전이다.

#### (마) 새로 필요한 것은 작다

1. **저장 중 재진입 가드** — 쓰기가 끝나기 전에 또 저장을 누르는 경우. 진행 중 플래그 하나 또는
   마지막 요청만 남기기. 몇 줄이다.
2. **"저장됨" 표시를 쓰기 완료에 건다** — 캡처 완료가 아니라. 쓰기 실패를 성공으로 표시하면 안 된다.
3. **멀티플레이에서는 서버가 캡처한다** — 클라이언트가 누르면 RPC. `RequestMeteorImpactRpc`
   (`LastShiftNetworkSandbox.cs:162`)가 그 형태의 선례다.

#### (바) `S-1a` 폐기로 **없어지는** 일

- 기존 전제였다면 **시뮬 정지 경로와 세션 종료 경로**를 만들어야 했다. 둘 다 필요 없어졌다.
- 협의 `10` 이 "`S-1a` 가 이 항목을 크게 줄인다 — 정지 후 다시 녹일 필요가 없다" 고 적었는데,
  **그 축소는 `S-1a` 가 폐기돼도 유지된다.** 이유만 바뀐다 — "정지하고 끝내니까" 가 아니라
  **"애초에 정지하지 않으니까"** 이고, 이쪽이 더 강한 근거다.

#### (사) 기획으로 넘길 것 하나 (기술 아님)

저장 버튼을 누른 뒤에도 플레이가 이어지므로, **파일에 담긴 것은 "버튼을 누른 순간" 이지 "플레이를
그만둔 순간" 이 아니다.** 플레이어가 "저장했으니 지금까지가 저장됐다" 로 오해할 여지가 있다.
기술 제약이 아니라 표시 문구 문제이므로 `game-planning` 소관으로 넘긴다.

### 1.5 분량

`LastShiftNetworkSnapshot` 이 `36`필드에서 대략 `60`필드로 는다. 전부 `float`·`bool`·`int`·`enum`
이고 새 자료구조가 없다. **작업일(`free-placement-runtime-chain-estimate-v1.md` §1 정의) 기준 `2`~`3`일**
로 본다 — 필드 배선과 플래그 분리이지 설계가 아니다.

`S-1a` 폐기로 인한 증감은 **`+0`** 이다. 논블로킹 캡처가 현행 동작이고(§1.4-가), 비동기 쓰기와
재진입 가드가 더해지는 대신 정지·종료 경로가 빠진다(§1.4-바).

> **§8.1 의 "9 가 불가능하면" 분기는 발동하지 않는다.** 저장 시점을 안전 지점으로 좁히는 안은 필요 없다.

## 2. 협의 `1` — 저장 포맷·위치

### 2.1 로컬 JSON 한 벌. 지금 직렬화 코드가 정말로 `0` 이다

`JsonUtility`·`Newtonsoft`·`PlayerPrefs` 사용처는 런타임에 **하나도 없다.** `System.IO` 는 `Du02*`
계측 러너 셋이 CSV 를 뱉는 데만 쓴다(`Du02RuntimeProbeRunner.cs:86`, `Du03ARuntimeProbeRunner.cs:59`,
`Du03BCRuntimeProbeRunner.cs:81`). **기존 포맷과 싸울 일이 없다** — 백지에서 고른다.

`JsonUtility` + `Application.persistentDataPath` 한 파일을 권고한다. 근거는 대상 자료의 모양이다:
저장 대상이 전부 `[Serializable]` 구조체와 원시값이고(`LastShiftShipState` 는 이미
`LastShiftSimulation.cs:47` 에서 `[Serializable]`), 사전도 다형성도 순환 참조도 없다 —
`JsonUtility` 가 못 하는 것들이 대상에 없다. 의존성을 늘릴 이유가 없다.

### 2.2 부동소수 정밀도는 관문이 아니다 — 여유가 오차보다 `10^5` 배 크다

문서가 새 고려사항으로 든 항목이다. **재 보니 관문이 아니다.**

판정선들을 실제로 꺼내 보면 결정 여유의 크기가 보인다:

| 판정선 | 값 | 자리 |
|---|---|---|
| 지배 문제 발동 | `>= 0.75` | `LastShiftSimulation.cs:338`·`:343`·`:348` |
| 미연결 전력 상한 | `0.40` | `LastShiftRecoveryTuning.UnpoweredBusCeiling` |
| 열 폭주 | `0.90` | `HeatRunawayTrigger` |
| 산소 사이렌 켬/끔 | `0.15` / `0.20` (**히스테리시스 밴드 `0.05`**) | `OxygenSirenTrigger` / `OxygenSirenRelease` |

**가장 좁은 여유가 `0.05` 규모다.** `float32` 왕복 오차는 상대 `~10^-7` 이므로 `0~1` 값에서
절대 오차가 `~10^-7` 이다. **다섯 자릿수 차이다.** 프리셋 튜닝 주석이 여유를 `cm` 단위로 재고 있는
것(`LastShiftSimulation.cs:190`–`:194`, "시계 여유 `79`cm / S-P1 여유 `77`cm")과 비교해도 같은 결론이다.

`0~1` 정규화가 아닌 유일한 값인 **도킹 진행도**(목표 `150` `thrust·s`, `LastShiftSimulation.cs:73`)도
상대 오차 `10^-7` 이면 절대 `1.5×10^-5` 다. `150` 짜리 예산에서 의미가 없다.

**권고는 그래도 왕복 보존 표기(`R`/`G9`)를 쓰는 것이다.** 판정이 위험해서가 아니라, 그게 한 줄이고
"정밀도 때문일 리 없다" 를 나중에 증명하지 않아도 되게 만들기 때문이다.
구현 카드 합격선: **저장→로드 후 B층 전 필드 비트 동일.**

### 2.3 측정 범위 확대분

A층(캠페인 전체 — 배·거점·자원 `4`종·해금)은 v1 답 그대로다. B층이 더하는 것은 위 `60`필드,
`JSON` 으로 대략 `2`~`3`KB 다. **파일 크기도 파싱 시간도 논의 대상이 아니다.**

## 3. 협의 `3` — 이어하기 씬 복원 시간

### 3.1 지금은 못 잰다. 복원 경로가 아직 없다

정직하게 적는다 — **없는 경로의 실행 시간은 측정할 수 없다.** 아래는 분해와 합격선이고,
실측은 구현 카드가 낸다.

### 3.2 v1.1 이 예산에 더한 몫은 사실상 `0` 이다

`10`초 예산이 셋으로 쪼개진다:

| 조각 | 비용 | 근거 |
|---|---|---|
| (가) 배치물 재조립 (`30`개 이상) | **예산을 다 쓰는 유일한 조각** | v1 에서 이미 측정 대상이던 것. 프리팹 인스턴스화·조립이 실제 비용 |
| (나) **B층 주입** | **마이크로초 단위** | `60`개 필드 대입 + `situationTracker.Evaluate` 한 번(`LastShiftSandboxController.cs:547`). 순수 산술이고 할당이 없다 |
| (다) **물리 정지 배치** | **무시 가능** | 대상이 아이템 `4`개와 승무원이다. `Transform` 쓰기 몇 번 |

**결론: v1.1 이 "측정 대상이 늘었다" 고 한 것은 맞지만, 늘어난 양이 예산 대비 무시할 수준이다.**
`10`초를 위협하는 것은 v1 때와 똑같이 **배치물 재조립 하나**이고, 조항 `S-7`·`S-8` 이 상쇄한다는
문서의 예상보다도 상황이 낫다 — 상쇄할 상승분 자체가 거의 없다.

**`10`초를 넘으면 성계 구성을 다시 본다** 는 §8.2 의 판단 기준은 유지하되, 그 판단은 **B층과 무관하게
배치물 수 하나로 결정된다.** 세이브가 성계 구성을 압박하지 않는다.

### 3.3 합격선

구현 카드에 붙일 것: **배치물 `30`개 + B층 주입 전체 경로를 `PlayMode` 에서 한 번 재고, 벽시계
`10`초 이하.** 측정 자리는 (가)/(나)/(다) 를 나눠 찍는다 — 넘었을 때 어디가 범인인지 알아야 한다.

## 4. 협의 `4` — 스키마 버전 (A/B 분리 · 부분 폴백 · 안내)

문서가 "가장 크게 오른다" 고 본 항목이다. **A/B 분리는 자연스럽고, 부분 폴백은 예상보다 싸다.**

### 4.1 A/B 경계가 이미 코드에 그어져 있다

두 층이 서로 다른 자리에 산다 — 억지로 나누는 게 아니다.

| 층 | 사는 곳 | 성질 |
|---|---|---|
| **A** (캠페인) | `LastShiftVoyage`(정적) · `LastShiftMaintenance`(정적) · `LastShiftPlacedModules`(정적) | 구간 회차·잔액·구매·배치물. **시뮬 튜닝과 무관하게 안정** |
| **B** (구간 런타임) | `LastShiftSandboxController` 인스턴스 상태 | 열·전력·압력·타이머. **튜닝 때마다 흔들린다** |

셋 다 `Clear()` 와 `ApplyNetwork*()` 를 이미 갖고 있다(§1.1 표). **A층만 실어 앉히는 것은 새 작업이
아니라 기존 훅 호출이다.**

### 4.2 B층 폴백의 목적지가 이미 생성 가능한 상태다 — 이게 이 항목을 싸게 만든다

부분 폴백의 어려운 부분은 보통 "버린 뒤 무엇으로 채우는가" 다. 여기선 답이 이미 있다:

```
LastShiftPresetFactory.Create(preset)   // LastShiftSimulation.cs:160 — 구간 시작 배 상태
LastShiftVoyage.EnterSegment(n)         // LastShiftVoyage.cs:124   — 구간 회차만 옮기고 원장은 안 건드린다
```

**"구간 시작" 은 저장해서 얻는 상태가 아니라 만들어 낼 수 있는 상태다.** 그래서 B층 폴백은
"B를 버리고 이 두 줄을 부른다" 로 끝난다. 플레이어가 잃는 것은 **그 구간의 진행분 하나**이고
캠페인은 온전하다.

`EnterSegment` 가 원장을 건드리지 않는다는 것이 여기서 결정적이다(주석이 그 규약을 명시한다) —
폴백이 잔액을 초기화하거나 수입을 두 번 넣지 않는다.

### 4.3 확인한 A→B 의존 하나 — 깨끗하게 풀린다

B를 버려도 A가 성립하는지 봐야 한다. 걸리는 지점이 하나 있었다:

`LastShiftMaintenance.ArriveAtPort(latches, towed)` 의 `latches` 는 **B층에서 파생된다** —
`LatchCount` 가 구역 압력과 봉인 여부로 매번 다시 센다(`LastShiftSandboxController.cs:203`–`:215`).
B를 버리면 이 값을 낼 수 없다.

**그런데 문제가 되지 않는다.** 구간 판정 순간에 그 수가 이미 A층으로 접혀 들어가기 때문이다 —
`LastShiftVoyage.SettleSegment` 가 `LastLatchCount` 에 박아 두고(`LastShiftVoyage.cs:166`), 그 값은
정적 프로퍼티로 남는다(`:70`). **A층 저장 대상에 `LastLatchCount` 를 포함하면 의존이 끊긴다.**

> 구현 카드가 지켜야 할 불변식으로 적을 것: **A층 필드는 B층을 참조해 재계산하지 않는다. 파생이
> 필요한 값은 판정 순간에 접어서 A층에 넣는다.** `LastLatchCount` 가 그 선례다.

### 4.4 권고 형태

```jsonc
{
  "schemaA": 1,           // 캠페인층. 드물게 오른다
  "schemaB": 1,           // 시뮬층. 튜닝마다 오른다
  "campaign": { … },      // A
  "segment":  { … }       // B — 없어도 로드된다
}
```

- **`schemaB` 불일치** → `segment` 를 버리고 A만 싣는다. 구간 시작으로 복원(§4.2). **안내한다.**
- **`schemaA` 불일치** → 명시적 실패. 조용한 부분 로드를 하지 않는다.
- **`segment` 키 부재** → 오류가 아니라 정상 경로. 기항에서 저장한 세이브가 이 모양이다.

안내 UI 는 §6.5 소관이고 기술 제약은 없다. **문구가 말해야 하는 것은 하나다 — "이번 구간 진행이
초기화됐고 항해는 그대로다".**

## 7. 협의 `10` — 저장 시점의 네트워크 권위 (`2026-08-09`)

> `S-1a` 폐기 후 다시 받은 항목. 질문은 **"저장 버튼 → 틱 경계 권위값 복사 → 백그라운드 직렬화가
> `4`인 환경 어디서 일어나는가"** 이고, 요구는 둘이다 — **체감 정지 `0`(가)** 와 **스냅샷 일관성(나)**.

**결론: 축소가 유지된다. 클라이언트에 아무것도 묻지 않는다.** 다만 기획이 근거로 든
"저장 대상이 전부 호스트 권위값(`S-2`)" 은 **정확하지 않다.** 두 갈래가 소유자 권위다(§7.2).
**그런데도 요구 (나)는 깨지지 않는다** — 그 이유가 §7.3 이고, 이 답의 핵심이다.

### 7.1 캡처가 일어나는 자리는 네트워크가 아니라 컨트롤러다

이게 "어디서 일어나는가" 의 답이고, **틀리면 단독 플레이에서 저장이 안 되는 자리**다.

**단독 플레이에는 서버가 없다.** `LastShiftNetworkSandbox` 는 네트워크 씬 빌더만 붙인다
(`LastShiftNetworkSceneBuilder.cs:66`). 솔로 씬과 `EditMode` 팩토리는 `LastShiftSandboxController`
를 맨몸으로 세운다. 그러므로 **캡처를 `PublishSnapshot()` 에 얹으면 안 된다** — 그 함수는
`IsServer` 가 참일 때만 도는 자리다(`LastShiftNetworkSandbox.cs:54`).

| | 캡처 주체 | 버튼을 눌렀을 때 |
|---|---|---|
| 단독 | 컨트롤러 (그 자리에서) | 바로 캡처 |
| `4`인 · 호스트가 누름 | 호스트의 컨트롤러 | 바로 캡처 |
| `4`인 · 클라가 누름 | **호스트의 컨트롤러** | 요청 `RPC` → 호스트가 캡처 |

요청 `RPC` 는 선례가 있다 — `RequestMeteorImpactRpc`(`LastShiftNetworkSandbox.cs:162`)가
`RequireOwnership = false` 로 같은 모양을 이미 쓴다.

> **캡처 함수는 컨트롤러(+정적 A층)를 읽는 순수 함수 하나이고, 네트워크가 정하는 것은
> "누가 그 함수를 부르는가" 뿐이다.** 이 분리가 `S-2`(호스트가 세이브를 소유한다)를 세 경로에서
> 같은 코드로 지키게 한다.

### 7.2 정정 — 저장 대상이 전부 호스트 권위값은 아니다

기획이 "저장 대상이 전부 호스트 권위값이라(`S-2`) 클라이언트를 세울 이유가 없어 보인다" 고
적었다. **결론은 맞지만 근거는 틀렸다.** 포즈 계열이 소유자 권위다:

```csharp
// LastShiftOwnerNetworkTransform.cs
protected override bool OnIsServerAuthoritative() => false;
```

- **아이템** — 잡히는 순간 소유권이 잡은 클라이언트로 넘어간다
  (`LastShiftNetworkGrabbable.cs:94` `NetworkObject.ChangeOwnership(player.OwnerClientId)`).
- **플레이어(=승무원)** — 같은 컴포넌트를 쓴다(`LastShiftNetworkPlayer.cs:69`·`:331`).

그래서 **§1.3 이 "새로 저장해야 한다" 고 든 아이템 실제 좌표와 승무원 위치는, 호스트에서 보면
`RTT` + 보간만큼 지난 값이다.** 시뮬 스칼라(열·압력·진행도)는 전부 호스트가 굴리므로 이 문제가 없다.

### 7.3 그래도 일관성 요구가 깨지지 않는 이유 — 시뮬이 이미 그 지연된 값으로 판정한다

여기가 이 항목이 안 커지는 지점이다.

```csharp
// LastShiftSandboxController.cs:831
crew.Tick(IsZoneVacuum(targetPlayer.transform.position), deltaTime);
```

**진공 판정의 입력이 이미 그 복제된 포즈다.** 호스트는 원래부터 지연된 승무원 위치로 산소를 깎아
왔다. 그러니 **저장이 시뮬보다 더 최신인 값을 뜰 이유가 없다** — 뜨면 오히려 파일이 판정과
어긋난다.

요구 (나)를 정확히 다시 쓰면 이렇다:

> **"실시간의 한 시점" 이 아니라 "시뮬이 본 한 tick" 이면 된다.** 그리고 §1.4-(나) 대로 캡처와
> `AdvanceMission` 이 둘 다 메인 스레드 동기 호출이라 **후자는 이미 보장된다.**

**남는 오차는 표시상이고 판정에 안 닿는다.** 보행 `3`m/s · 지연 `100`ms 면 아이템이 최대 `30`cm
어긋난 채 저장될 수 있는데:

- 고정 여부(`secured`)는 **호스트가 쓰는 `NetworkVariable`** 이고 로드 때 좌표로 재계산하지 않는다.
- `SecureDistance`(`0.9`m, `LastShiftSandboxController.cs:10`) 검사는 **고정을 시도하는 순간에만**
  돌지 저장·로드 경로에 없다.
- 속도를 복원하지 않으므로(`S-7`) 로드 후 그 자리에 정지 배치된다.

> 요약: **소유자 권위 때문에 클라이언트를 세우거나 값을 되받아 올 이유가 없다.** 세우면 오히려
> 요구 (가)(체감 정지 `0`)를 스스로 깨고, 얻는 것은 판정에 쓰이지도 않는 `30`cm 다.

### 7.4 캡처는 `LateUpdate` 여야 한다 — 이건 실제 요구사항이다

들린 아이템의 포즈가 **`LateUpdate` 에서** 홀더 소켓에 붙는다(`LastShiftNetworkGrabbable.cs:72`–`:83`).
`Update` 에서 캡처하면 **아이템이 홀더보다 한 프레임 뒤인 조합**이 저장된다. 자기모순 스냅샷은
아니지만(§7.3 의 기준으로는 통과한다) 굳이 어긋난 조합을 파일에 남길 이유가 없다.

**권고: 캡처를 `LateUpdate` 에 두고 `DefaultExecutionOrder` 로 `LastShiftNetworkGrabbable` 뒤에
고정한다.** 한 줄이고, §1.4-(나)가 "고정하면 이득은 있다" 고 적어 둔 것이 여기서 **선택이 아니라
권고**가 된다.

### 7.5 백그라운드 직렬화 경계 — A층까지 안전하다

§1.4-(라)가 B층에 대해 세운 경계가 **A층에도 그대로 선다.** A층 셋 전부 값이다:

- `LastShiftPlacedModule` 은 **씬 참조가 `0`** 이다 — 발자국 `6`값 + 구역 + 카탈로그 인덱스
  (`LastShiftPlacedModules.cs:13`, 요약 주석이 그 규약을 명시한다).
- `LastShiftVoyage`·`LastShiftMaintenance` 는 정적 스칼라와 구매 목록이다.

**그래서 A+B 를 통째로 워커에 넘길 수 있다.** 메인 스레드에서 읽어야 하는 것은 §1.4-(라)가 든
`Transform`·`Rigidbody` 뿐이고, 그건 캡처 단계 안에 있다.

### 7.6 조항 `S-11` 확인 — 안전하다. 대신 조건 하나가 붙는다

**"A층 쓰기 빈도가 늘어도 문제없는가" → 문제없다. 빈도가 사실상 안 는다.**

A층 변이점을 전부 꺼내 보면 **하나도 구간 중에 있지 않다**:

| 변이점 | 자리 | 언제 |
|---|---|---|
| `SettleSegment` | `LastShiftSandboxController.cs:759` | 구간 판정 순간 |
| `ArriveAtPort` | `LastShiftPlacementUi.cs:262` | 기항 진입 |
| `TrySpend` / `TryChargeModule` / `TryRefundModule` | `LastShiftMaintenance.cs:168`·`:192`·`:222` | 기항 UI |
| `Register` | `LastShiftCompartments.cs:536` | 씬 조립 |
| `EnterSegment` | `LastShiftSandboxController.cs:1307` | 구간 진입 |

**구간 중에는 A층이 한 글자도 안 변한다.** 그러므로 비행 중 수동 저장의 A층 쓰기는 **같은 값
재기록**이고, 비용은 `JSON` 몇 `KB` 추가일 뿐이다. `S-11` 이 실제로 값을 하는 자리는 **기항에서
사고 나서 저장할 때**이고, 그건 조항이 노린 바로 그 경우다.

> **붙는 조건 — `S-11` 은 §4.3 불변식과 함께 읽어야 한다.**
> 수동 저장이 구간 **중**에 A층을 쓸 때, `LatchCount` 를 **그 자리에서 다시 세어 넣으면 안 된다.**
> 구간 중 래치 수는 판정 전 값이라, 그걸 `LastLatchCount` 로 저장하면 **폴백 후 기항 수입이
> 달라진다**(`LastShiftMaintenance.IncomeFor(latches)`). **A층 캡처는 접힌 값을 그대로 복사하는
> 것이지 재계산이 아니다** — §4.3 이 세운 불변식이 `S-11` 에서 처음으로 실제 위험이 된다.

### 7.7 협의 `10` 난이도

**축소 유지. 새 계통 없음.** 필요한 것 넷이고 셋은 §1.4-(마)와 겹친다:

1. 캡처 함수를 컨트롤러 쪽에 둔다 (§7.1) — **겹치지 않는 새 항목**
2. 캡처를 `LateUpdate` 로 고정 (§7.4) — 한 줄
3. 클라 요청 `RPC` (§1.4-마-3)
4. 재진입 가드 (§1.4-마-1)

**증분은 §1.5 의 `2`~`3`일 위에 `+0.5`일 이내다.** 설계가 아니라 배선이다.

### 7.8 협의 `10` 밖으로 둔 것

**로드 시 클라이언트 절차**(호스트가 세이브를 실으면 접속 중인 클라이언트를 어떻게 맞추는가)는
저장 시점이 아니라 복원 시점 문제라 이 답에 넣지 않았다. `S-2`(클라이언트는 세이브를 안 가진다)
때문에 **파일 쪽 위험은 아니고**, 남는 것은 "재접속인가 인-플레이스 재주입인가" 라는 연출·흐름
선택이다. **필요하면 별도로 받겠다.**
