# 자유 배치 — 배치 커서 소유권 (v1)

> 상태: `game-tech-director` 결정 v1 · `2026-08-08` · 카드 `865bf53f`([LAST SHIFT] 자유배치 UI — 배치 확정 흐름)
> 답하는 것: `free-placement-expansion-feasibility-v1.md` §12-9 — "2인 이상 협동 환경에서 배치 커서를 누가 조작하는가, 동시 배치 시도를 어떻게 처리하는가"
> 구현물: `LastShiftPlacementAuthority` · `LastShiftPlacementCursor` · `LastShiftPlacementUi`

---

## 0. 결론 먼저

**커서는 한 번에 한 명이 잡는다. 먼저 잡은 쪽이 갖고, 뺏기는 없다.**

그리고 **동시 배치 시도는 애초에 위험하지 않다** — 이 조사의 실질 결과가 이쪽이다. 표는
이미 안전하다. 잠그는 이유는 표가 아니라 **씬과 화면**이다.

---

## 1. 실측 — 무엇이 실제로 위험한가

§12-9 를 받았을 때 예상한 위험은 "둘이 같은 자리에 동시에 넣으면 겹친 방이 표에 들어간다"
였다. **아니다.**

```csharp
// LastShiftCompartments.TryRegister
verdict = Judge(candidate);          // ← 확정하는 그 순간 다시 잰다
if (!verdict.Accepted) return false;
```

`TryRegister` 는 커서가 미리 재 둔 판정을 **안 믿는다.** 확정 시점에 지금 표로 다시 판정하고,
통과한 것만 넣는다. 그래서 둘이 같은 자리를 동시에 눌러도 두 번째는 첫 번째가 넣은 방과
겹쳐서 물린다. **표 층에는 경합 문제가 없다.**

위험은 세 곳에 있고 전부 표 밖이다.

| 위험 | 자리 | 무엇이 되는가 |
|---|---|---|
| **씬 재조립이 전역이다** | `LastShiftModuleAssembler.Rebuild` | 배치된 방 **전체**를 지우고 다시 세운다. 둘이 번갈아 확정하면 서로의 방이 매번 지워졌다 서고, 그 사이 `LastShiftBakedDoorways` 가 구멍을 메웠다 다시 뚫는다 |
| **미리보기가 하나다** | `LastShiftPlacementUi` 의 유령 상자 | 커서가 둘이면 화면의 상자가 누구 것인지 안 갈린다. 확정된 방과 남의 미리보기가 같은 자리에 겹쳐 보인다 |
| **판정 캐시가 낡는다** | `LastShiftPlacementCursor` | 커서는 매 프레임 판정을 다시 재지 않는다(§2). 옆 사람이 그 자리를 채운 순간 **내 화면의 "배치 가능" 이 낡은 표를 근거로 남는다** |

셋째가 가장 조용하다. 표는 옳게 물리므로 배는 안 망가지지만, **화면이 초록인데 Enter 가 안
먹는다.** 배치한 사람은 자기 입력이 씹혔다고 읽는다.

---

## 2. 그래서 커서는 표 개정 번호를 같이 본다

```csharp
// LastShiftPlacementCursor.Refresh
if (!dirty && cachedRevision == LastShiftCompartments.Revision) return;
```

판정을 캐시하는 것은 비용 때문이다 — `Judge` 는 부를 때마다 표를 판정기 입력으로 옮겨 담고
(배열 하나), 매 프레임 부르면 그 배열이 매 프레임 쓰레기가 된다. 커서 상태가 바뀌었을 때와
**표 `Revision` 이 올랐을 때**만 다시 잰다.

**뒤 조건이 이 문서가 코드에 남긴 실물이다.** `LastShiftCompartments.Revision` 은 축 B 가
"표 사본을 든 쪽이 자기 사본이 낡았는지 묻는 자리" 로 만들어 둔 것인데, 그 첫 사용처가 여기다.
`LastShiftPlacementCursorTests.AnotherCursorsCommitInvalidatesMyCachedVerdict` 가 고정한다.

## 3. 잠금 규약

| | |
|---|---|
| 잡기 | `TryClaim(clientId)`. 비어 있으면 잡고, 남이 잡고 있으면 **물린다** |
| 다시 잡기 | 자기가 이미 잡고 있으면 성공이다 — 화면을 다시 여는 것이 실패면 안 된다 |
| 놓기 | `Release(clientId)`. **자기 것만** 놓는다 |
| 뺏기 | **없다** |
| 강제 해제 | `Revoke()`. 호스트 전용 |

### 3.1 왜 뺏기를 안 두는가

뺏기가 되면 **확정 직전에 커서가 사라지는 자리**가 생긴다. 판정을 통과한 배치가 이유 없이
안 들어가는 것으로 보이고, 그 화면에는 원인이 안 적힌다. 기항은 판 밖이라 시간 압박이 없으므로
(§4 아래) 뺏어야 할 이유도 없다.

### 3.2 왜 강제 해제는 두는가

잡은 사람이 접속을 끊고 나가면 아무도 배치를 못 한다. 그 상태는 **기항을 벗어날 방법이 없다** —
`RG-3`(회복 경로가 없는 상태를 만들지 않는다)을 항해 층에 적용한 것과 같은 취지다.

---

## 4. 이 결정이 서 있는 전제

**배치는 기항에서만, 판 밖에서만 일어난다.** 추정 §8 과 `voyage-run-structure-v1.md` §4 의
전제를 그대로 받았다. 그래서:

- 실시간 경합이 아니다. 한 명이 커서를 잡고 나머지가 보는 동안 **말로 합의**한다 —
  §6 사례 E("넷이 여력 2 를 두고 갈린다. 이 게임에서 처음으로 팀이 말로 합의해야 하는 자리")가
  기대하는 장면이 그것이고, 커서를 넘기는 것이 그 합의를 화면에 드러내는 가장 싼 방법이다.
- 커서 위치를 네트워크로 흘릴 필요가 없다. 확정 결과만 동기화하면 된다.

**판 안에서 배치가 가능해지면 이 문서 전체가 무효다.** 추정 §8 이 같은 말을 적어 뒀다 —
모듈 목록이 네트워크 상태가 되고 `Resolve` 오버레이가 클라이언트마다 갈릴 수 있다.

## 5. 아직 안 한 것

**네트워크 배선이 없다.** `LastShiftPlacementAuthority` 는 정적 전역이라 **한 프로세스
안에서만** 성립한다. 진짜 2인 이상에서 돌려면 호스트가 권위를 갖고 클라이언트의
잡기/놓기/확정 요청을 RPC 로 이 함수들에 옮겨야 하고, 확정 결과(표 한 칸)를 클라이언트에
복제해야 한다.

**그 배선이 없는 지금도 이 잠금은 두 가지를 한다.** 같은 클라이언트가 화면을 둘 여는 것을
막고, **소유권 규약을 코드에 고정한다.** 규약이 값으로 있어야 RPC 를 붙일 때 옮길 대상이 있다 —
규약이 문서에만 있으면 붙이는 사람이 다시 정하게 되고, 그때 §12-9 는 두 번째로 미결이 된다.

같이 안 한 것:

- **기항 화면 자체.** 정비 여력·고정 목록·가격(`voyage-run-structure-v1.md` §4.2)은
  `game-planning` 몫이다. `LastShiftModuleCatalog` 의 다섯은 tech 가 고른 그레이박스
  치수이고 기획 정본이 아니다.
- **부모 잠금 상태.** 잠긴 문 뒤에 모듈을 붙이면 지금은 통과한다. 기항 개방이 그 문을 열
  것이므로 영구 불통은 아니지만, "지금 못 들어가는 방을 산다" 가 허용인지는 기획 판단이다.
- **모듈 이동(재배치).** 표는 넣기와 빼기만 있고 옮기기가 없다. 커서에 `ignoreIndex` 경로가
  이미 판정기에 있으므로(`LastShiftPlacementRules.Evaluate`) 붙일 자리는 열려 있다.
