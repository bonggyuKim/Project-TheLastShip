# 적 함선 내구의 상태 모양 (v1)

> `campaign-scale-and-combat-balance-v1.md` §8-`1` 에 대한 `game-tech-director` 답이다.
> 질문: **적 함선 내구를 `0`~`1` 스칼라로 두는 것이 시뮬 구조에 맞는가.**
> 조건: 조우 진행도가 B층 저장 대상이므로 **읽고 쓸 수 있어야 한다**(협의 `7`·`11`).

## 0. 결론

**`0`~`1` 스칼라가 맞다. 다만 값 하나가 아니라 둘이어야 한다.**

| 이름 | 범위 | 사는 곳 | 성질 |
|---|---|---|---|
| `EnemyHullIntegrity` | **`0`~`1`** | **B층**(구간 스냅샷) | 조우 진행도. 매 틱 깎이고 저장·복원된다 |
| `EnemyHullCapacity` | `1.00`~`1.30` | **A층**(성계 번호에서 파생) | 성계 강도 계수. 조우 안에서 안 변한다 |

**한 값으로 두면 §8-`9` 에서 깨진다.** 그 항목이 "성계 `10` 부터 적 내구 `1.00 → 1.30`" 을 열어 뒀는데, `0`~`1` 이라는 범위는 **최대치가 `1` 이라는 전제**를 값 안에 박아 넣은 것이다. 강도를 같은 값에 얹으면 `1.30` 이 범위를 깨고, 그 순간 이 문서가 아래에서 세는 이득 셋이 전부 사라진다.

---

## 1. 왜 `0`~`1` 스칼라가 맞는가 — 새 규약이 아니다

시뮬의 함선 상태(`LastShiftSimulation.cs` 의 `LastShiftShipState`)는 **계기 전부가 이미 `[Range(0f, 1f)] float`** 이다.

```csharp
[Range(0f, 1f)] public float BusPower;
[Range(0f, 1f)] public float OxygenPressure;
[Range(0f, 1f)] public float HullIntegrity;
[Range(0f, 1f)] public float EngineHeat;
[Range(0f, 1f)] public float FuelReserve;
```

**적 내구를 같은 모양으로 두면 새로 정하는 것이 하나도 없다.**

1. **감쇠·적분 코드가 대칭이 된다.** `LastShiftRecoveryTuning` 의 상수는 전부 *초당 `0`~`1` 변화량*이고(`HeatRisePerSecond 0.020`, `OxygenLeakPerSecond 0.024`, …), 무기 전력 소모(§6.2 `0.045+0.10`)와 교전 길이(§6.1 `72`초)도 같은 축의 값이다. 적 내구가 `0`~`1` 이면 **초당 감소량 하나가 곧 교전 길이**라 §6.1 이 그은 `60`~`90`초 창을 상수 하나로 검산할 수 있다.
2. **인터페이스가 이미 있다.** HUD 게이지·경보 임계값(`OxygenSirenTrigger 0.15` 류)이 전부 `0`~`1` 을 읽는 코드라, 적 내구 막대가 기존 게이지와 **같은 위젯**으로 그려진다.
3. **B층 왕복이 필드 하나다.** `LastShiftSaveFile.cs` 의 `LastShiftSegmentSave` 는 `JsonUtility` 로 통째 직렬화되므로 `float` 필드 하나를 더하는 것이 전부다. 스키마 상수(`SchemaB`)를 올릴 필요도 없다 — **필드 추가는 `JsonUtility` 에서 하위호환**이고(옛 파일은 `0` 으로 읽힌다), 값이 `0` 인 옛 세이브는 어차피 조우가 없던 파일이다.

§8-`1` 이 단 조건("읽고 쓸 수 있어야 한다")은 그래서 **비용이 사실상 `0` 이다.**

---

## 2. 왜 값이 둘이어야 하는가

**`0`~`1` 의 값어치는 "범위가 고정"이라는 것 하나에서 나온다.** 강도를 같은 값에 얹으면 그게 깨지고, 깨지는 순간 §1 의 이득 셋이 차례로 죽는다.

| 얹었을 때 | 무엇이 죽는가 |
|---|---|
| 최대치가 성계마다 다르다 | HUD 막대가 **성계마다 다른 길이**를 뜻한다. "절반 깎았다"가 성계 `9` 와 `10` 에서 다른 남은 시간이 된다 |
| `[Range(0f, 1f)]` 를 못 쓴다 | 인스펙터 · 클램프 · 기존 게이지 위젯이 전부 예외 처리 대상이 된다 |
| 교전 길이 검산이 안 선다 | §6.1 의 `72`초를 상수 하나로 못 잰다. 성계별로 다시 곱해야 한다 |

**둘로 나누면 셋 다 산다.** 데미지는 정규화해서 들어간다:

```text
EnemyHullIntegrity -= 초당피해 * dt / EnemyHullCapacity
```

성계 `10` 의 `1.30` 은 **`0`~`1` 막대가 `1.30`배 천천히 줄어드는 것**으로 읽히고, 막대 자체는 성계와 무관하게 같은 뜻을 유지한다.

**저장은 `EnemyHullIntegrity` 하나면 된다.** `EnemyHullCapacity` 는 성계 번호에서 나오는 파생값이라 A층에 **적을 필요조차 없다** — 성계 번호는 이미 A층에 있다. 이게 §8-`1` 의 조건을 가장 싸게 만족시키는 형태다: **B층에 `float` 하나.**

---

## 3. 배치 — 어느 클래스에 사는가

**`LastShiftShipState` 에 넣지 않는다.** 그 구조체는 *우리 배*의 계기이고, `LastShiftDamageResolver` · `LastShiftMeteorApplication` 이 전부 그 전제로 서 있다. 적 값을 끼우면 운석 판정이 적 배를 읽는 모양이 되고, 그건 §8-`1` 이 물은 "시뮬 구조에 맞는가"에 **안 맞는다**는 쪽의 답이 된다.

**별도 조우 상태 하나를 신설한다** — `LastShiftMaintenance` 가 여력 원장을 별도 정적 상태로 세운 것과 같은 판단이다(그 파일 상단 "왜 신설인가"). 근거도 같다:

- 조우는 **구간 안**의 물건이라 구간이 끝나면 리셋된다 → B층 스냅샷 대상, A층 아님.
- 시뮬의 물리·자원 축과 **값이 오가는 경로가 없다.** 적 내구가 우리 배 계기를 직접 안 바꾼다(피격은 §6.4 의 관통 → `HullIntegrity` 경로로 들어오지, 적 내구에서 나오지 않는다).
- 그래서 **끼우는 것보다 옆에 세우는 것이 작다.**

## 4. 안 정한 것

- **`1.30` 의 확정 여부는 `game-balance` 몫이다**(§8-`9`). 이 문서는 **그 값이 나중에 무엇이 되든 `0`~`1` 막대를 안 깨는 자리**를 정했을 뿐이다.
- 조우 진행도 중 내구 **말고** 무엇이 더 B층에 들어가는가(적 사격 쿨다운·회피 상태 등)는 전투 구현 카드에서 같이 센다. 이 문서는 §8-`1` 이 물은 값 하나만 답한다.
