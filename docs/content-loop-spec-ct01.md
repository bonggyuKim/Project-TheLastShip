# CT-01 컨텐츠 루프 설계 결정서

> 상태: 결정안 v0.2 · 2026-08-07 · 카드 `4d3d4b03-b592-47cb-9bf3-6c54b1e6a2ed` (v0.2는 SP-01 카드 `0fb18e77` 확인 반영)
> 상위 정본: `docs/concept-draft.md`, `docs/prototype-execution-plan.md`
> 이 문서는 기획 결정만 담는다. 구현 지시는 PM 승인 후 별도 카드로 나간다.

**v0.1 → v0.2 변경 이유.** SP-01 플레이 피드백에서 "조작은 되는데 지금 뭐가 문제인지 화면에서 못 읽는다"는 지적이 나왔다. 코드를 확인한 결과 이건 **새 설계가 필요한 문제가 아니다** — §5(`R4`)가 `v0.1`에서 이미 이 문제를 진단하고 고쳤어야 할 것(원시 숫자 덤프 → 임계선 막대 + 구역 등급)을 정했는데, 그 구현이 안 됐을 뿐이다. `LastShiftSandboxController.OnGUI`는 지금도 `v0.1` §0.1이 지적한 원시 덤프 그대로다(`thrust=`/`bus=`/`hull=` 등 텍스트, `F3` 디버그 토글 없음, 구역 칸도 등급이 아니라 정확한 압력 소수점을 상시 노출). 추가로 `ship-elements-and-situations-v1.md`(v0.3)와 `corridor-4p-redesign-v1.md`(v2)가 구역을 `3`(조종석/엔진실/산소실)에서 `4`(조종석/전력실/냉각실/산소실)로 늘려서, §5.2/§5.3의 구역 수·개구부 수 서술도 갱신이 필요하다. §5.6이 이 둘을 함께 정리한다.

## 0. 결론

사용자 판정 "뭐하라는지 모르겠어"의 원인은 지시문 부재가 아니다. **플레이어가 상태를 되돌릴 수 있는 행동이 코드에 존재하지 않는 것**이 원인이다. 따라서 CT-01은 HUD 문구 설계가 아니라 다음 세 가지를 게임 규칙으로 확정하는 작업이다.

1. **수리 동사** — 아이템을 상태 회복 수단으로 승격
2. **상태 악화 tick** — 정적 상태에 시간축 부여
3. **성공·실패 판정** — 6분 타이머에 결과 부착

이 셋이 없으면 아무리 좋은 HUD를 붙여도 "알려줬는데 할 게 없음"으로 악화된다.

### 0.1 현재 코드 상태 (근거)

| 확인 위치 | 사실 |
|---|---|
| `LastShiftSimulation.cs:232-235` | resolver는 아이템 `Secured`·위치를 **입력으로 읽기만** 한다. 고정해도 `EngineHeat`·`BusPower`·`OxygenPressure`가 바뀌지 않는다 |
| `LastShiftSandboxController.cs:210-214` | 플레이어가 상태를 바꿀 수 있는 유일한 경로는 `ApplyControl(thrust, attitude)` 뿐이다 |
| `LastShiftMeteorApplication.Apply` | 운석 1회 적용 후 상태는 **정지**한다. 악화도 회복도 없다 |
| `LastShiftSandboxController.cs:124,147` | `dockingSecondsRemaining`은 6분에서 감소만 하고, 0 도달 시 아무 판정도 하지 않는다 |
| `LastShiftSandboxController.cs:326` | 플레이어 HUD가 `thrust= bus= O2= hull= heat= attitude= damage=` 원시 수치 덤프다 |
| `LastShiftSandboxController.cs:278-281` | 프리셋별 loose 아이템이 1:1 대응한다. `Tether`는 상시 loose |

### 0.2 기존 자산 판정

**전부 유지한다. 폐기하는 것은 없다.**

- 프리셋 3종(`HighHeatHighThrust` / `PowerOverloadLooseBattery` / `BadAttitudeHighOxygen`) — 유지
- FIRST DOMINANT 분기 3종(`CoolingCouplingDetached` / `BatteryDisplacedBusDisconnected` / `SideOxygenLeak`) — 유지
- 아이템 4종(`Tether` / `CoolingCanister` / `Battery` / `PatchPlate`) — 유지

다만 아이템의 **역할을 확장**한다. 현재는 resolver 입력값이지만, 앞으로 복구 수단이 된다. 기존 resolver 계약(`LastShiftResolverInput`)은 그대로 두고 회복 경로를 추가하는 방향이므로 기존 EditMode/PlayMode 테스트는 유지된다.

## 1. 수용 기준 1 — 진입 30초 안에 목표 파악

### 1.1 3층 전달 구조

| 층 | 시점 | 전달물 | 채널 |
|---|---|---|---|
| L1 목적 | 진입 0~5초 | 어디로 가는가, 무엇이 성공인가 | 조종석 창밖 도킹 스테이션 + HUD 목표 줄 |
| L2 사건 | 운석 전후 | 무엇이 망가졌는가 | 물리 연출 + 구역 경고등 + HUD 1행 |
| L3 행동 | 손상 지점 접근 시 | 지금 여기서 무엇을 누르는가 | 국소 상호작용 프롬프트 |

### 1.2 L1 상세 (진입 0~5초)

플레이어는 조종석에서 시작한다. 전방 창에 도킹 스테이션 실루엣이 보이고, HUD 최상단에 한 줄이 상시 표시된다.

```text
목표 — 추력 30% 이상 · 산소 20% 이상으로 도킹      DOCK T-5:00
```

이 한 줄이 "어디로", "무엇을 지켜야", "얼마나 남았는가"를 동시에 전달한다. 숫자 7개 덤프를 이 한 줄로 대체한다.

### 1.3 L3 상세 — 정답 아이콘 금지 규칙과의 경계

`concept-draft.md:164`는 "경고 아이콘이 정답 도구와 위치를 모두 알려주는 수리"를 금지한다. CT-01은 다음 경계로 이를 지킨다.

- **알려준다:** 어디가 이상한가 (구역 단위), 지금 들고 있는 물건으로 여기서 할 수 있는 조작이 있는가
- **알려주지 않는다:** 어떤 물건을 가져와야 하는가, 세 회복 경로 중 어느 것을 택해야 하는가, 어느 손상을 먼저 처리해야 하는가

#### 통로 층 — 구역 안도 밖도 아닌 위치

`36m` 레이아웃에서 구역 사이에 통로가 생기면서 **L3에 위치 층이 하나 늘어난다.** 기존 L3는 "구역 안"과 "구역 밖" 둘뿐이었는데, 통로는 어느 쪽도 아니다.

| 위치 | 읽히는 것 | 성격 |
|---|---|---|
| 구역 안 | 원인 진단 + 상호작용 프롬프트 | 행동할 수 있는 자리 |
| **통로** | **앞뒤 개구부의 등급(`6m`) · 수치(`2m`)** | **비교할 수 있는 자리** |
| 구역 밖·통로 밖 | 없음 | — |

**이 층이 없으면 통로는 그냥 복도이고, 거리를 늘린 것이 `concept-draft.md:165`(장거리 왕복)에 걸린다.** 판정 조건 `(다) 왕복 중 판단이 없다`를 거짓으로 만드는 것이 정확히 이 층이다. 상세는 §5.3.

**정답 아이콘 금지와의 경계는 위 표와 같다.** 통로에서 늘어나는 것은 "어느 쪽이 급한가"뿐이며, "무엇을 가져가야 하는가"는 여전히 어느 층에서도 알려주지 않는다.

구체 예시 — 엔진실 냉각 coupling 앞에서:

| 플레이어 상태 | 표시 |
|---|---|
| 빈손 | `냉각 결합부 이탈 — 연결부 규격 불일치` (무엇이 필요한지 이름을 대지 않음) |
| `CoolingCanister` 소지 | `[E] 제자리 연결 (4.0s)` / `[F] 임시 결속 (0.8s)` |
| `PatchPlate` 소지 | 프롬프트 없음 |

즉 물건을 들고 오면 선택지가 열리고, 어느 선택지를 쓸지는 남은 시간과 다른 손상 상황을 보고 플레이어가 판단한다.

### 1.4 30초 안에 파악되는지 검증법

Editor 플레이에서 사용자가 다음 3개를 말로 답할 수 있어야 통과한다.

1. 나는 어디로 가야 하는가
2. 성공 조건 2개는 무엇인가
3. 지금 이 순간 정상인 구역과 이상한 구역은 어디인가

## 2. 수용 기준 2 — 성공·실패 조건과 압박 요소

### 2.1 판정 조건

| 결과 | 조건 |
|---|---|
| **성공 (정상 도킹)** | 도킹 트리거 진입 시점에 `ThrustDemand ≥ 0.30` **AND** `OxygenPressure ≥ 0.20` |
| **성공 (절충 생환)** | 위 조건 충족. 단 회복 경로에서 `성능 포기`를 1회 이상 사용 — 결과 요약에 포기 항목 명시 |
| **실패 (질식)** | `OxygenPressure ≤ 0.00` 도달 |
| **실패 (표류)** | 타이머 0 도달 시 도킹 미달 |
| **실패 (추력 부족)** | 타이머 0 시점에 `ThrustDemand < 0.30` |

즉사는 없다. 실패는 모두 타이머 만료 또는 서서히 진행되는 산소 고갈로만 발생한다. `concept-draft.md:198`의 회복성 규칙을 지킨다.

### 2.2 압박 요소 선택 — 시간 + 누적 손상 (자원 제외)

**자원 압박은 P0에서 쓰지 않는다.** 이유: 소모품 관리가 들어오면 "왕복해서 채우기"로 수렴하기 쉽고, `concept-draft.md:165`의 금지 규칙과 정면 충돌한다.

**시간과 누적 손상을 결합**한다. 시간만으로는 "여유롭게 다 고치고 기다리기"가 되고, 손상만으로는 급박함이 안 생긴다.

### 2.3 상태 악화 tick — CT-01의 핵심 추가

현재 상태는 운석 후 정지한다. 이를 **3개의 서로 다른 실패 시계**로 바꾼다.

| 계통 | 악화 조건 | 악화 효과 | 플레이어가 잃는 것 |
|---|---|---|---|
| 열 | `ThrustDemand > 0.60`이고 냉각 미복구 | `EngineHeat +0.020/s` | `EngineHeat ≥ 1.00`이면 엔진 보호 발동, `ThrustDemand` 상한 `0.25`로 강제 잠금 → **추력 성공선을 잃는다** |
| 산소 | 파공 미봉합 | `OxygenPressure -= 0.006 × (1 - HullIntegrity) / 0.5` 매초 | 20% 성공선까지의 **시간을 잃는다** |
| 전력 | 배터리 bus 미연결 | `BusPower ≤ 0.40` 유지 | 조향 응답 0.5s 지연 + 산소 펌프 회복 정지 → **다른 두 복구의 속도를 잃는다** |

세 시계가 서로 다른 것을 뺏는 것이 설계 의도다. 열은 성공 자체를 불가능하게 만들고, 산소는 남은 시간을 깎고, 전력은 복구 효율을 떨어뜨린다. 따라서 우선순위 판단이 매 run 달라진다.

### 2.4 타이머 값 권고

현재 `6f * 60f` = 360초를 **300초(5분)로 축소**한다. 근거: P0 목표는 5~7분 항해이고, 6분에 악화 tick까지 없으면 압박이 0이다. 300초는 세 프리셋 모두에서 "두 손상 중 하나는 임시 우회로 넘겨야" 하는 압력을 만든다. 실제 값은 `game-balance` 검증 대상으로 남긴다.

## 3. 수용 기준 3 — 운석 사건의 관측 형태

### 3.1 채널 배분 원칙

**원인은 물리로, 진단은 국소 시각·청각으로, 종합은 HUD로.** HUD가 원인을 설명하면 물리 연출이 무의미해지고 `concept-draft.md:196`의 "원인과 물리 반응이 화면에서 보여야 한다"가 무너진다.

### 3.2 타임라인

#### T-20s ~ T-3s (예고)

| 채널 | 내용 |
|---|---|
| 시각 | 창밖 좌현 방향에 광점 1개. 시간에 따라 각크기 증가 |
| 청각 | 근접 경보 비프. 간격이 `1.5s → 0.3s`로 축소 |
| HUD | `근접 물체 · 좌현 · T-20` 카운트다운 1행 |

이 20초 동안 플레이어는 회피(자세 조정), 감속(추력 하강), 물건 고정, 계속 가속 중 하나를 택한다. 이것이 세 프리셋에서 첫 지배 문제를 갈라놓는 결정 창이다.

#### T-3s ~ T-0 (직전)

| 채널 | 내용 |
|---|---|
| 시각 | 광점이 화면 좌측을 채움 |
| 청각 | 비프 정지 → 정적 0.5s |
| HUD | 카운트다운 사라짐 |

의도적 정적을 넣어 충격을 강조한다.

#### T+0 (충격)

| 채널 | 내용 |
|---|---|
| 시각 | 화면 흔들림 0.8s, 좌현 방향 임팩트 플래시, 고정 안 된 물건이 실제로 굴러감 (`LastShiftGrabbable.ApplyImpact` 기존 구현 활용) |
| 청각 | 충격음 + 구역별로 다른 잔향 길이 |
| HUD | **아무것도 표시하지 않는다** |

#### T+0 ~ T+2s (정보 공백, 의도적)

HUD에 진단이 뜨지 않는다. 플레이어는 소리와 물리 반응만으로 "무슨 일이 났지"를 판단한다. 이 2초가 `concept-draft.md:27`의 "대화가 가장 빠른 정보 전달 수단"을 실제로 강제한다. 2인 플레이에서 이 구간에 첫 대화가 나오는지가 협동 성립의 1차 신호다.

#### T+2s ~ T+3s (구역 경보)

| 채널 | 내용 |
|---|---|
| 시각 | 손상 구역에 국소 현상 발생 — 냉각: 백색 증기 분출 / 전력: 스파크 + 조명 점멸 / 산소: 안개 + 파공 방향 흐름 |
| 청각 | 해당 구역에서만 크게 들리는 지속음. 다른 구역에서는 감쇠 |
| HUD | 구역 표시 3칸 중 해당 칸이 색 변화 |

#### T+3s 이후 (국소 진단)

**HUD는 구역 이름까지만, 정확한 진단은 그 구역에 들어가야 읽힌다.**

| 위치 | 읽히는 정보 |
|---|---|
| 조종석 HUD | `엔진실 이상` (무엇이 이상한지는 안 나옴) |
| 엔진실 진입 후 | `냉각 결합부 이탈 — 연결부 규격 불일치` |

이것이 `concept-draft.md:27`의 "정보는 구역에 귀속된다"를 구현하는 최소 형태이며, 동시에 3인 이상에서 세 번째 사람이 정보 채널로 기능하는 근거가 된다.

### 3.3 CT-02와의 경계

| 항목 | CT-01 소관 | CT-02 소관 |
|---|---|---|
| 운석 예고 | 20초 길이, 정보량, 채널 배분 | 광점·궤적·스케일 연출 형상 |
| 충격 | 정적 0.5s + 공백 2s 타이밍 | 흔들림 곡선, 플래시, 사운드 |
| 구역 구획 | 국소 정보 경계선 위치, **시야 차단 요구** | 씬 형상, 문·통로 배치 |
| 저중력 | 관여하지 않음 | 중력 값 |

**시야 차단은 CT-01 소관이다.** 형상은 CT-02가 정하지만 **"구역 간 직선 관통 시선이 없어야 한다"는 요구 자체는 국소 정보 규칙에서 나온다.** 판정 조건과 확정 좌표는 §5.3과 `ship-scale-and-density-v1.md §3.5`에 있다.

**저중력 값에 CT-01이 의존하는 지점이 하나 있다.** 물건이 충격으로 굴러가는 거리가 복구 난이도를 직접 결정한다. `PatchPlate`가 산소실 밖으로 나가버리면 `Tether` 회수가 필수가 되고, 방 안에 머무르면 회수 단계가 사라진다. CT-02의 중력·마찰 확정값을 받은 뒤 "물건 최대 이동 거리"를 CT-01에서 후속 조정해야 한다.

**이 항목은 `36m` 치수에서 재계산 대상이다.** 구역 길이가 `11m` / `14m` / `11m`가 되면서 두 가지가 바뀐다.

1. **방 안에 머무를 확률이 올라간다.** 같은 초기 속도로 굴러가도 방이 길어졌으므로 개구부에 도달하기 전에 멈출 여지가 커진다. `Tether` 회수 단계가 사라지는 쪽으로 기운다
2. **일단 나가면 회수 비용이 커진다.** 나간 물건을 되찾는 데 `ZONE_TRANSIT 3.5초` 왕복이 붙는다

즉 **"거의 안 나가지만 나가면 비싸다"**로 분포가 바뀐다. 이것이 바람직한 방향인지는 `game-balance` 판정 대상이며, 나가는 빈도가 너무 낮으면 `Tether`가 사문화되고 너무 높으면 `RG-4 (6)`의 조종석 봉합판 이탈 조합에 걸린다.

## 4. 수용 기준 4 — 1~4인 역할 분화 근거

### 4.1 혼자서 안 되는 이유 — 역할 잠금이 아니라 시간 상충

직업이나 전용 능력을 두지 않는다(`concept-draft.md:157`). 대신 **한 사람이 동시에 두 자리에 있을 수 없다**는 사실만으로 협동을 만든다.

핵심 상충 구조:

```text
조종석에서 추력을 낮추면 → 열 상승이 멈춘다
그러나 추력이 낮으면 → 도킹까지의 시간이 늘어난다
엔진실에서 냉각을 연결하면 → 열이 실제로 내려간다
그러나 연결에는 두 손이 필요하고 → 그동안 조종 입력이 없다
```

`LastShiftControlHold`의 8초 유지가 솔로 순차 해결을 허용한다. 하지만 조종석→엔진실 왕복 + 4.0초 제자리 연결이 8초를 넘는다. 따라서 솔로는 `임시 결속(0.8s)`을 선택하거나 여러 번 왕복해야 하고, 매번 열이 다시 오른다. **솔로는 가능하지만 명백히 느리고 후유증이 남는다.**

#### 이 부등식은 현재 씬에서 거짓이었다 — 치수가 근거다

**CT-01의 협동 성립 근거 전체가 위 부등식 하나에 걸려 있는데, 작성 시점 씬에서 그 부등식이 성립하지 않았다.**

```text
                   왕복        안전 복구   합계     hold 8초
현재 씬 (12.5m)   2 x 1.0s  +  4.0s   =  6.0초   <  8초   ← 거짓
새 치수 (36m)     2 x 3.5s  +  4.0s   = 11.0초   >  8초   ← 참
```

구역 중심 간격이 `4m`이고 `MoveSpeed 4f`이므로 편도가 `1.0초`였다. 즉 **솔로가 안전 복구를 하고 돌아와도 hold 가 `2초` 남는다.** "느리고 후유증이 남는다"가 아니라 아무 대가가 없었고, `임시 결속`을 고를 이유도 없었다. 2인 분업이 편의였지 필요가 아니었다는 뜻이다.

**`ZONE_TRANSIT 3.5초`는 이 부등식에서 역산한 값이다.** 정본은 [`ship-scale-and-density-v1.md` §2.1](./ship-scale-and-density-v1.md)이며 유도는 다음과 같다.

```text
(1) 2t + REPAIR_TEMP <= 8.0    임시 우회는 솔로로 가능해야 한다   -> t <= 3.6
(2) 2t + REPAIR_SAFE >  8.0    안전 복구는 솔로로 불가능해야 한다 -> t >  2.0

대역 (2.0, 3.6] 의 상단인 3.5초 채택. 솔로 왕복 후 0.2초 여유
```

**두 부등식이 함께 있어야 §4.2의 1인 행이 성립한다.** `(2)`만 만족시키면 솔로가 안전 복구를 못 하는 것에 그치지만, `(1)`까지 만족시켜야 "임시 결속으로는 되지만 그 대가로 `60초` 후 재이탈을 떠안는다"는 선택이 생긴다. `t`가 `3.6`을 넘으면 임시 결속마저 hold 안에 못 들어와 솔로에게 선택지가 사라진다.

### 4.2 인원별 구조

| 인원 | 성립 구조 | 구체 상황 |
|---|---|---|
| 1인 | 순차 해결. 8초 hold + 임시 결속 | 추력 0.3으로 낮추고 hold 걸고 뛰어가서 임시 결속 → 60초 후 재이탈 → 다시 왕복. 도킹은 되지만 절충이 강제됨. **`0.2초` 여유로 성립한다** — §4.1 대역 유도 참조 |
| **2인 (P0 코어)** | 자리 분업 | A가 조종석에서 추력을 0.35로 유지하며 열 상승을 늦추는 동안 B가 냉각통을 제자리 연결(4.0s). A가 추력을 올리면 B의 연결이 끊어질 수 있어 **말로 타이밍을 맞춰야 한다** |
| 3인 | 정보 채널 + 운반 | 국소 정보 규칙 때문에 두 구역을 동시에 읽을 수 없다. C가 산소실 상태를 읽고 조종석에 전달하면 A가 우선순위를 바꾼다. 대기가 아니라 관측이 역할이다 |
| 4인 | 2팀 분리 + 전력 경합 | 두 손상이 동시 진행되는 프리셋에서 팀이 갈린다. 단 `BusPower`가 공유 자원이므로 한 팀의 복구가 다른 팀의 펌프 회복을 늦춘다 |

### 4.3 P0 구현 범위

**2인만 구현한다.** 1인은 시스템 회귀 검증용으로 유지하고, 3·4인은 위 근거만 문서에 남기고 Gate P0 Continue 이후에 연다. `prototype-execution-plan.md:304`의 제외 범위와 일치한다.

### 4.4 2인 성립 판정 기준

다음이 관찰되어야 협동 PASS다.

1. 충격 후 2초 정보 공백 구간에서 **먼저 말을 건다**
2. 한쪽의 추력 조작이 다른 쪽 작업 성패를 **1초 안에** 바꾼다
3. 두 사람 모두 최소 2구역을 방문한다
4. 어느 쪽도 20초 이상 대기하거나 같은 입력을 반복하지 않는다

## 5. 수용 기준 5 — HUD 정보 구성

### 5.1 분리 원칙

**플레이어 HUD는 계통 상태를 원시 숫자로 보여주지 않는다.** 현재 `LastShiftSandboxController.cs:326`의 7개 숫자 덤프는 전량 디버그 층으로 이동한다.

### 5.2 플레이어 HUD (상시, 4요소)

```text
┌──────────────────────────────────────────────────────┐
│ 목표 — 추력 30% · 산소 20% 이상으로 도킹    DOCK T-3:42│  ← 1. 목표 줄
│                                                      │
│ 추력  ██████▌│░░░░░░░░                               │  ← 2. 임계선 있는 막대
│ 산소  ████████████│░░░░                               │  ← 3. 임계선 있는 막대
│                                                      │
│ [조종석]  [엔진실 ▲]  [산소실]                        │  ← 4. 구역 3칸
└──────────────────────────────────────────────────────┘
```

**요소별 규칙**

| 요소 | 표시 | 숫자 노출 |
|---|---|---|
| 목표 줄 | 성공 조건 2개 + 남은 시간 | 시간만 `M:SS` |
| 추력 막대 | 막대 + `30%` 위치 임계선. 임계선 아래면 막대 색 변화 | 없음 (막대 길이로만) |
| 산소 막대 | 막대 + `20%` 위치 임계선 | 없음 |
| 구역 3칸 | `정상`=무색 / `불안정`=노랑 / `고장`=주황 / `위기`=빨강 점멸 | 없음 |

임계선을 그림으로 보여주는 것이 핵심이다. `thrust=0.28`이라는 숫자보다 "막대가 선 아래에 있다"가 즉시 읽힌다.

구역 4단계는 `concept-draft.md:46`의 `정상 → 불안정 → 고장 → 위기` 어휘를 그대로 쓴다. 새 용어를 만들지 않는다.

### 5.3 국소 정보 — 판독 3단

기존 2단(구역 안 / 구역 밖)에 **통로 단을 추가한다.** 근거와 치수 정본은 [`ship-scale-and-density-v1.md` §3.1](./ship-scale-and-density-v1.md)이다.

| 거리 | 읽히는 것 | 용도 | 표면 |
|---|---|---|---|
| `6m` (통로 반대편) | **3단계 등급만** — `주의` / `위험` / `치명` | 비교용. 어느 쪽이 급한가 | 개구부 프레임 발광 띠 |
| `2m` 이내 (개구부 앞) | **정확한 압력 수치** | 결정용. 문을 열 것인가 | 개구부 프레임 게이지 |
| 구역 안 | **원인 진단 1행 + 상호작용 프롬프트** | 행동용. 무엇을 할 것인가 | 기존 국소 HUD |

**구역 밖에서 원인 진단과 프롬프트가 보이지 않는 것은 그대로다.** 위 두 단이 추가하는 것은 등급과 수치뿐이며, `concept-draft.md:164`의 정답 아이콘 금지에 걸리지 않는다 — 어느 구역이 급한지는 알려주고, **무엇을 가져가야 하는지는 여전히 알려주지 않는다.**

#### 왜 2단이 아니라 3단인가

2단(통로에서 읽힘 / 방에서 읽힘)이면 **통로에 들어서는 순간 정보가 한꺼번에 들어와 통로 안에서의 이동이 무의미해진다.** 3단이면 통로 중앙에서 판단이 하나 생긴다.

```text
B 가 통로 B 산소실 쪽 끝에서 반대쪽 개구부 2 의 게이지를 본다
  ->  엔진실 "위험" 등급만 보인다

  판단: 앞까지 가서 수치를 확인할 것인가, 지금 하던 일을 먼저 끝낼 것인가
  비용: 앞까지 1.38초 + 복귀 1.38초 = hold 8초 중 2.75초
```

**그 `2.75초`가 값이다.** 정보를 얻는 데 시간이 들고 그 시간이 hold 와 경쟁한다. §4.1이 요구한 시간 상충이며 2단 구조에서는 생기지 않는다.

#### 판독 표면은 개구부 `4`곳이다 — 압력 경계 `2`와 다르다

문은 `2`개다(경계가 둘이므로). 따라서 "양쪽 문을 비교한다"는 구조는 성립하지 않는다. **판독 표면을 문이 아니라 개구부 프레임에 걸고 그 수를 `4`로 둔다.**

```text
조종석 ─[개구부0]─ 통로A ─[개구부1]─ 엔진실 ─[개구부2]─ 통로B ─[개구부3]─ 산소실
                            ↑ 문·게이지                 ↑ 문·게이지
```

**개구부 `4`곳이 압력 경계를 늘리지 않는 이유** — 개구부 `0`·`3`은 통로와 방을 잇는 자리인데, 구역 경계가 `x = ±4`이므로 통로 A 는 통째로 조종석 구역, 통로 B 는 통째로 산소실 구역이다. 그 양쪽이 같은 구역이라 애초에 경계가 아니다. `ZonePressure` `3`, 문 `2`, `EQUALIZE_RATE` 대상 쌍 `2`, 격리 규칙 전부 불변이다.

**게이지는 개구부 `1`·`2`에만, 통로 쪽 한 면에만 붙는다.** 개구부 `0`·`3`은 양쪽이 같은 구역이라 게이지가 실을 정보가 없다(HUD 가 이미 상시로 준다). 양면으로 달면 엔진실 방 한가운데에서 세 구역이 다 읽혀 `166`이 깨진다.

**비교의 단위는 압력 경계가 아니라 시선이다.** 한 화면에 둘이 아니라 **내 구역(HUD)과 문 너머 구역(게이지)**이다. 통로에서는 둘이 보이고 방 안에서는 HUD 하나뿐이며, 그 차이가 통로의 정보 우위다.

#### 시야 차단 요구 — 신규 조항

**구역과 구역을 잇는 직선 관통 시선이 존재해서는 안 된다.**

이것은 미관이 아니라 국소 정보 규칙의 물리적 전제다. 조종석에 선 채로 엔진실 개구부가 보이면 등급이 읽히고, 그러면 `concept-draft.md:166`(한 방에서 계기판만 감시)이 참이 된다. **통로가 정보 우위 지점이라는 §5.3 전체가 무너진다.**

판정 기준은 통로 폭이 아니고, **조건이 하나가 아니라 둘이다.**

> **`GAP_Z`는 축선 관통을 막는다. 비축선 시선은 통로 배플이 막는다. 둘 다 있어야 이 조항이 성립한다.**

| 조건 | 값 | 막는 것 |
|---|---|---|
| `GAP_Z` | `≥ 0.4m` — 한 통로 안 두 개구부의 `z` 구간 간격 | 축과 나란한 시선 |
| 통로 배플 | `2`개. 통로를 가로지르는 폭 `1.6m` 판, 바닥~천장 불투명 | 벽에 붙어 비스듬히 겨눈 시선 |

`통로 폭 ≥ 개구부 폭 × 2`는 프록시이며 판정 기준으로 쓰지 않는다. 통로 폭 `3.6m`는 `GAP_Z`의 파생값이다. 확정 좌표와 배플 위치는 `ship-scale-and-density-v1.md §3.5`에 있다.

**`GAP_Z` 하나로는 부족하다는 것이 실측으로 확인됐다.** 조종석 우현 벽을 따라 띠가 남아 방 바닥의 `22%`에서 엔진실 개구부가 보이고, 안쪽 개구부를 먼저 지나는 두 방향은 `52%`다. **배플 `2`개는 장식이 아니라 이 조항을 성립시키는 부품이며, 옮기면 규칙이 조용히 깨진다.**

**단 배플이 통로를 개구부보다 좁게 만들면 안 된다.** 배플 옆 통행 폭이 `OPENING_WIDTH 1.6m` 미만이면 물건을 든 채 구역을 넘는 동작이 막히고, 그것은 §2.4 `CARRY_SPEED` 설계가 걸려 있는 동작이다. 현재 구현은 `1.0m`로 저촉 상태다(`ship-scale-and-density-v1.md §3.5`).

**꺾인 통로와 `6m` 판독선은 양립하는 정도가 아니라 같은 조건이다.** 통로 안에서 개구부 둘은 종 `6m` · 횡 `1.6m`로 떨어져 폭 `3.6m` 통로 안에서는 둘 다 시야에 들어오고, 방 안에서는 축선이 없고 비축선은 배플이 막는다. 꺾지 않으면 방에서도 읽히고, 꺾어야 통로에서만 읽힌다. **배플이 통로 안 시선은 안 막는다는 점이 핵심이다** — 막는 것은 개구부 둘을 *모두* 지나는 직선뿐이고, 통로에서 출발하는 시선은 그 집합에 없다.

### 5.4 디버그 HUD (`F3` 토글, 기본 OFF)

기존 정보를 **하나도 잃지 않고** 전량 이관한다.

```text
[DEBUG F3]
```

### 5.6 SP-01 확인 (v0.2) — 새 설계 아님, 미구현 확인 + 4구역 갱신

#### 5.6.1 결론 먼저

**국소정보 규칙과 안 부딪히는 방향은 이미 §5에 있다.** 이번 요청에 새 설계는 필요 없다 — §5(`R4`)가 정한 대로 구현하고, 구역 수만 `3`에서 `4`로 갱신하면 된다. PM이 제안한 원칙("개인 상태는 상시, 남의 구역 상태는 가야 보임")도 이미 §5.2(구역 등급은 상시·전 구역)와 §5.3(정확한 진단은 거리별 `3`단)로 정확히 그 형태로 짜여 있다.

#### 5.6.2 왜 지금 못 읽는가 — 진단

`LastShiftSandboxController.cs`의 `OnGUI`를 확인했다. 지금 화면에 나오는 건 `v0.1` §0.1이 이미 지적했던 바로 그 원시 덤프다:

- `INPUT state: thrust=0.xx bus=0.xx hull=0.xx heat=0.xx attitude=xx damage=0.xx` — 계통 상태가 전부 소수점 텍스트다. 막대·임계선이 없다
- 구역 칸(`DrawZonePressureCells`)이 등급(`정상`/`불안정`/`고장`/`위기`)이 아니라 **정확한 압력 소수점**(`CKPT 0.62` 등)을 전 구역·상시로 보여준다 — §5.2가 정한 "등급만, 숫자 없음"과 반대다
- `F3` 디버그 토글이 코드에 없다 — 이 전부가 항상 켜진 하나의 화면이다

**즉 §5가 이미 맞는 방향을 정했는데 구현이 안 됐다.** 사용자가 "임시 HUD 경고 신호가 아니라 제대로 된 상태 UI"라고 표현한 게 정확히 이 상태를 가리킨다.

#### 5.6.3 국소정보 규칙과의 관계 — 왜 안 부딪히는지 재확인

PM의 질문("자기 개인 상태는 상시, 다른 구역 상태는 가야 보임")에 그대로 답한다 — 이미 §5가 이 원칙을 두 층으로 나눠 갖고 있다.

| 층 | 무엇을 보여주는가 | 상시/조건부 | 국소정보 위반 아닌 이유 |
|---|---|---|---|
| 개인 상태 | `SuitOxygen`(§5.4의 N8 막대), 추력·산소(선내 공용 계기, 조종석 계기판 값) | 상시 | 자기 자신·조종석 계기판 값이지 남의 구역 비밀이 아니다 |
| 구역 등급(`4`칸) | `정상`/`불안정`/`고장`/`위기` **카테고리만** | 상시, 전 구역 | 이미 있는 `전선 사이렌`과 같은 층위다 — "어디가 급한지"는 알려주고 "왜·얼마나"는 안 알려준다 |
| 정확한 진단 | 정확한 수치(`2m` 개구부) → 원인 1행+프롬프트(구역 안) | 거리 조건부(§5.3 `3`단) | `166` 규칙이 실제로 막는 지점이 여기다 — 정확한 값과 원인은 가야만 나온다 |

**지금 코드의 문제는 셋째 층(정확한 수치)이 첫째·둘째 층과 안 갈리고 전부 섞여 상시로 나온다는 것이다.** 등급 층만 상시로 두고 수치·원인 층을 거리로 가두면 국소정보 규칙은 그대로 유지된다.

#### 5.6.4 4구역 갱신 — §5.2/§5.3 서술 교체

`corridor-4p-redesign-v1.md`(v2, §2~§3)가 확정한 대로 구역은 `4`개(조종석/전력실/냉각실/산소실), 개구부는 `5`곳, 문은 `3`개, 게이지는 개구부`1`·`3`에 붙는다(§5.2/§5.3의 "구역 `3`칸"·"개구부 `4`곳"·"게이지는 개구부 `1`·`2`"는 전부 이 값으로 교체한다):

- **구역 등급 칸**: `3`칸 → **`4`칸**(`[조종석] [전력실] [냉각실] [산소실]`), 각 칸은 여전히 `정상`/`불안정`/`고장`/`위기` 카테고리만
- **판독 표면**: 개구부 `4`곳 → **`5`곳**, 문 `2`개 → **`3`개**. 게이지는 개구부`1`(통로A↔전력실)·`3`(냉각실↔통로B)에 — 신설 개구부`2`(전력실↔냉각실)는 게이지가 없다(양쪽 다 방이라 통로 쪽 면이 없다는 기존 규칙, `corridor-4p-redesign-v1.md` §3)
- **개구부`2`(전력실↔냉각실) 판독 예외**: 이 문은 `corridor-4p-redesign-v1.md` §19.2가 이미 정한 대로 배플이 아니라 **문 개폐 상태**가 차단을 전담한다 — §5.3의 `6m`/`2m` 거리 판독 `2`단은 이 문에는 적용하지 않는다. 문이 닫혀 있으면 완전 차단, 열려 있으면 두 방이 서로 보인다(그래도 동시에 읽는 구역은 `2`개뿐이라 `SIMUL_ZONES ≤ 2` 유지)
- **나머지 `4`개 개구부**(`0`·`1`·`3`·`4`)는 §5.3의 `6m`/`2m`/구역 안 `3`단 그대로 적용

#### 5.6.5 우선순위 — 이미 있는 R4를 지금 실행

이 카드는 새 결정이 필요한 게 아니라 **`v0.1` §5(`R4`) + 위 `4`구역 갱신을 그대로 구현**하면 끝난다. SP-01 검증이 이걸로 막혀 있다는 점을 고려해 우선순위를 최상위로 올리길 권한다 — `game-tech-director`에게 "새 HUD를 설계해 달라"가 아니라 "§5.2/§5.3(v0.2 갱신 반영)을 그대로 구현해 달라"로 전달하면 된다.

#### 5.6.6 미결 사항

1. 구역 등급 임계값(압력 값 → `정상`/`불안정`/`고장`/`위기` 구간 경계)의 구체 수치 — `game-balance`(`concept-draft.md:46` 어휘의 구체 임계값이 아직 없다면)
2. 개구부`2`(전력실↔냉각실) 판독 예외가 실제 플레이에서 이상하게 느껴지지 않는지 — 씬 완성 후 체감 판정
3. `F3` 디버그 토글 구현 — `game-tech-director`
