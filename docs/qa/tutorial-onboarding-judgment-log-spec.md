## 1. 태그 둘

### `[LAST_SHIFT_TUTORIAL]` — 단계 전환

```
[LAST_SHIFT_TUTORIAL] step=<n> action=ENTER|LEAVE|COMPLETE elapsed=<s>
```

- 발생: 단계 전환마다 `1`줄(조항 `T-9`). `LastShiftTutorial.cs:262`·`369`·`381`.
- `elapsed` 는 **튜토리얼 시작 기준 누적**이다. `BeginVoyage` 에서 `0` 으로 서고(`:226`) 단계가 바뀌어도 안 끊긴다 — 리셋되는 것은 `stepElapsed` 뿐(`:378`).
- **버전 표시가 없다.** 열거형 재매김(`+2`) 전후 로그를 줄 안에서 구분할 수단이 없다 → `schema=` 키 추가를 `game-tech-director` 에 요청 중.

### `[LAST_SHIFT_PATROL]` — 순회 결과

```
[LAST_SHIFT_PATROL] action=CLOSE played=4/4 approached=1/4 seconds=31.2 floor=12.4 missed=none
```

- 발생: 순회가 닫히는 자리에서 **판당 `1`줄**. `LastShiftPatrolNarration.cs:210`. 프레임 계기가 아니다.
- 구간은 `AI_T_01`(광장 진입) → `AI_T_11` 이다. **기상이 안 들어간다.**

| 필드 | 뜻 | 판정 |
|---|---|---|
| `played` | 기능 줄이 화면에 떴는가 | **판정값 아님.** 조항 `N-8` 로 거의 항상 `4` — `4`가 아니면 버그다 |
| `approached` | 설비 앞까지 걸어갔는가 | **판정값.** 합격선 `4/4` |
| `seconds` | 실제 순회 소요 | 진단값(3절) |
| `floor` | 순회 이론 최소 | `FloorSeconds = 12.4`(`:67`) |
| `missed` | 빠진 방 | `played` 파생이므로 `played=4/4` 면 항상 `none` |

**두 값의 판정 기준이 다르다(조항 `N-11`).** 조종석에서만 갈린다 — `played` 는 `스크린 시야 진입`, `approached` 는 `스크린 앞 도달`이다. 스크린은 문턱에서도 보이므로 대사는 그때 떠야 맞고 공간 판정은 따로 잰다. **조종석에서만 두 값이 갈리는 것이 정상이다.**

## 2. 판정 축은 둘이다

| 축 | 값 | 로그 |
|---|---|---|
| 시간 — 단계 `1`~`2` | `75`초 이하 | `step=1 ENTER` → `step=3 ENTER` 의 `elapsed` 차 |
| 시간 — 단계 `3`~`12` | `150`초 이하 | `step=3 ENTER` → `step=12 ENTER` 의 `elapsed` 차 |
| 공간 — 순회 | `approached = 4/4` | `[LAST_SHIFT_PATROL]` |

**`elapsed` 필드의 차로 잰다** — 줄 순서나 벽시계가 아니다. 값이 누적이라 로그가 다른 출력과 섞이거나 중간 줄이 유실돼도 안 깨진다.

**`seconds`/`floor` 를 독립 판정 축으로 쓰지 않는다**(`game-balance`). 합격 케이스(`approached=4/4`)에서는 이미 시간이 대본대로 경로에 묶여 분해능이 없다.

**마지막 단계는 구멍이 아니다.** `step=12 ENTER` 가 시간 축 B 의 종료선이면서 옛 §6 판정 `3`(자율 배치 `60`초)의 시작선이다 — `LastShiftTutorial.cs:350-351` 이 그렇게 못박아 뒀고, 뒤따르는 `COMPLETE` 가 그 판이 플래그를 받았다는 증거다.

**판 경계는 추가 필드 없이 잘린다.** `AdvanceTo` 가 `step <= Step` 을 되돌리므로(`:344`) 단계가 단조 증가한다 → `step` 이 증가하지 않는 줄이 새 판의 시작이다.

**전환 이전 로그는 측정 근거로 쓰지 않는다.** 단계 `1`~`2` 구간은 옛 로그에 존재한 적이 없고(기상·순회가 신규), 단계 `3`~`12` 는 오프셋(`옛 1~10` → `새 3~12`)으로 읽히지만 읽을 원본이 EditMode 테스트 산출물뿐이다. 두 상한 모두 **전환 이후 로그로만** 잰다.

## 3. 해석식 — `approached < 4` 의 원인 가리기

`game-balance` 산출. **합격을 가르는 값이 아니다.**

```
기대 순회 시간 = 12.4 + 7.0 × approached

  n=0  12.4    n=1  19.4    n=2  26.4    n=3  33.4    n=4  40.4~43.4
```

| `seconds` 대비 | 읽는 법 | 손잡이 |
|---|---|---|
| 기대보다 크게 높다 | 헤맨 것 | 재촉 `12` → `8`초 |
| 기대보다 낮다 | 훑은 것 | 설계 문제 아님 |

참조값(v1.24 정정 후): 순회 **최소 `12.4`** · 대본대로 **`43.4`** · 최악 **`66.4`** 초. `n=4` 의 상단 `43.4` 는 `ScriptPathSeconds`(`:77`, `3.34 × 13`)이고 대본을 다 읽는 경로의 값이다.

**재플레이는 구조적으로 걸러진다.** 순회 상태기가 `IsArmed`(무장 && `!HasCompleted`)를 요구하므로 끝낸 판은 이 로그를 아예 안 낸다. 완료 전에 그만두고 다시 시작한 판은 플래그로 못 가리지만 `seconds` 가 `floor` 에 붙는 것으로 읽힌다.

### 3-1. 확인 대기 — `28.4` 의 출처가 없다

`game-writer` 핸드오프가 "`approached=4/4` 가 이미 최소 `28.4`초를 강제한다"고 적었는데, **`28.4` 는 정본 어디에도 없다.** 식으로는 `n=4` 가 `40.4`(상단 `43.4`)이고 정본 참조값은 `12.4`/`43.4`/`66.4` 다. 같은 문장의 "추가로 재는 것이 `3`초뿐" 은 `43.4 − 40.4 = 3.0` 으로 설명되므로, `28.4` 만 근거가 없다.

**v1.24 에서 같은 유형이 한 번 있었다** — `floor=24.4` 를 썼는데 그건 순회 값이 아니라 단계 `1`~`2` 합계(기상 `12.0` + 순회 `12.4`)였다. `game-balance` 확인 필요. 결론(판정 축을 시간 + `approached` 둘로 두는 것)은 이 수와 무관하게 성립한다.

### 3-2. 코드에 폐기된 수가 남아 있다

`LastShiftPatrolNarration.cs:208` 주석이 아직 `최속 경로(24.4초)` 라고 적고 있다. v1.24 가 폐기한 값이다(순회 최소는 `12.4`). 로그를 읽는 사람이 코드 주석을 근거로 삼으면 분모가 두 배 틀린다 → `game-tech-director` 주석 정정 요청.

## 4. 상시 라인은 단계 진행이 아니라 상태다

`AI_F_W1`~`W4` 는 어느 블록에도 안 들어간다(`50 = 블록 46 + 상시 4`). 재현 검수를 시퀀스가 아니라 상태 케이스로 잡는다.

| 케이스 | 조건 | 확인 |
|---|---|---|
| `W1` | 선외 슈트 산소 `45%` 도달 | 판당 `1`회 · `CHIME_ALERT` |
| `W2` | 선외 슈트 산소 `35%` 도달 | 판당 `1`회 · 화면 임계 점멸과 같은 프레임 |
| `W3` | `O-7` 자동 회수 발동 | 발동선은 `0` 이 아니라 `EvaReturnReserve 0.02` |
| `W4` | `W3` 후 `2`초 | 튜토리얼 기항 한정(`T-8`) — 평시에 뜨면 거짓말 |

`W1`·`W2` 가 판당 `1`회이므로 `W3` → `W4` 로 열리는 두 번째 EVA 는 무경고다. 의도 확인 대기(검수 보고서 `S3-4`).
