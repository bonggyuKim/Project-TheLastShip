# The Last Ship 진행 구조 정정 (v1) — 도킹 제거 · 함선 누적 · 세이브/이어하기

> 상태: `game-planning` 정정안 v1 · `2026-08-10` · 사용자 직접 재확인
> 게임명: **The Last Ship**. 저장소·코드의 `LastShift*` 식별자는 마이그레이션 전 내부 이름으로만 남긴다.
> 상위 정본: `campaign-structure-20h-and-save-v1.md`의 함선 누적·세이브 결정, `core-four-rooms-and-hull-schematic-v1.md`, `outboard-outpost-and-map-final-v1.md`, `tech/save-backbone-stage1-v1.md`, `tech/save-backbone-stage2-v1.md`
> 이 문서가 대체하는 범위: 기존 문서의 **도킹 목표·도킹 게이지·도킹 래치·도킹 판정·도킹 결과 화면**과 이를 전제로 한 보상·밸런스 계산

## 0. 결론

1. **도킹은 The Last Ship의 현재 진행 구조에서 제거한다.** 도킹 스테이션 진입, `DockProgress`, `DockTargetThrustSeconds`, 도킹 래치 `0~4`, `SuccessNominalDocking`/`SuccessCompromised`를 게임의 목표·보상·결과로 설명하지 않는다.
2. **진행의 본체는 한 척의 함선이 장기 항해 동안 누적되는 것이다.** 배·거점·자원·손상·배치·결정은 짧은 런 종료 때 초기화되지 않는다.
3. **코어 루프는 `항해 중 사건/조우 → 현장 수습 → 결과 누적 → 기항 → 인양·정비·보급 → 함선/거점 확장 → 저장·이어하기`다.**
4. **세이브는 부가 편의가 아니라 누적 진행의 필수 백본이다.** 호스트가 A층 캠페인 상태와 B층 구간 스냅샷을 소유하고, 수동 저장 중에도 플레이는 계속된다.
5. **기존 도킹 코드가 존재한다는 사실은 기획 유지 근거가 아니다.** `LastShiftVerdict`, `DockProgress`, 결과 화면은 초기 프로토타입의 잔여 구현이며 후속 마이그레이션 대상이다.

## 2. 새 진행 구조

### 2.1 층

| 층 | 정의 | 저장 |
|---|---|---|
| **구간** | 사고나 조우 하나를 현재 함선 상태로 감당하는 짧은 플레이 단위 | B층 스냅샷 |
| **기항** | 인양·정비·보급·배치를 결정하는 판 밖의 준비 지점 | A층 자동 저장 |
| **성계** | 여러 구간과 기항으로 이루어진 한 세션 분량의 장 | A층 진행 |
| **항해** | 출발부터 최종 목표 지점까지 이어지는 전체 여정 | A층 전체 |

`campaign-structure-20h-and-save-v1.md`가 확정한 **리셋 없음 · 성계 `12`개 · 전체 약 `20`시간 · P1 성계 `1~2`** 구조는 유지한다. 바뀌는 것은 각 구간을 도킹 판정으로 끝내지 않는다는 점이다.

### 2.2 플레이 루프

```text
현재 함선 상태로 항해
→ 사고·환경·타 선박 조우
→ 현장 진단과 협동 수습
→ 손상·자원·선택이 함선에 누적
→ 기항
→ 선외 인양·정비·보급
→ 선체·거점 자유배치
→ 자동 저장 / 필요 시 수동 저장
→ 같은 함선으로 다음 구간
```

### 2.3 장기 목표

한 판의 도킹 성공이 아니라 **팀이 만든 한 척의 함선을 최종 목표 지점까지 유지·확장하며 데려가는 것**이 목표다. 성계 하나의 종료와 전체 항해의 종료를 같은 결과 카드로 처리하지 않는다.

## 3. 함선 확장

### 3.1 확장이 진행인 이유

- 새 방의 위치가 사고 지점까지의 거리와 우회 경로를 바꾼다.
- 기능 모듈의 선택이 전력·열·산소·정비의 우선순위를 바꾼다.
- 선외 거점 확장이 기항에서 같은 시간에 회수할 수 있는 자재량을 바꾼다.
- 한 번 확정한 배치는 저장되어 다음 접속과 다음 성계에서도 같은 함선으로 남는다.

숫자 보너스만 오르고 동선·계통·협동이 바뀌지 않는 모듈은 진행 축으로 인정하지 않는다.

### 3.2 자원 역할

| 자원 | 현재 역할 |
|---|---|
| 정비 여력 | 함선에 붙이는 방·기능 모듈 |
| 자재 | 손상 복구·보급·선외 거점 확장 |
| 산소 | 앞으로 버틸 수 있는 구간 수 |
| 식량 | 장기 항해 지속 가능성 |

**정비 여력의 획득량을 도킹 래치로 계산하던 규칙은 폐기한다.** 대체 획득 규칙은 §6 미결 `1`에서 새로 확정한다. 확정 전까지 기존 `MaxLatches`·`IncomeFor(latches)` 수치를 새 기획의 근거로 사용하지 않는다.

## 4. 세이브와 실패

### 4.1 유지하는 세이브 결정

- 세이브는 호스트 하나가 소유한다. 개인 캐릭터 진행은 없다.
- 수동 저장은 언제든 가능하고 플레이를 멈추지 않는다.
- A층은 성계 진행·함선/거점 배치·자원·튜토리얼 상태를 담는다.
- B층은 현재 열·압력·사건 진행·물건 상태를 담는다.
- B층을 읽지 못하면 B만 버리고 A층 함선 진행은 보존한다.

### 4.2 실패와 저장의 분리

수동 저장은 **다음 접속에서 이어하기 위한 지점**이고 실패를 무르는 체크포인트가 아니다. 실패 시 되감기 기준은 직전 기항 자동 저장으로 유지한다.

다만 기존 실패 이름 `FailureAdrift`·`FailureInsufficientThrust`·`FailureAsphyxiation`은 도킹 판정을 전제로 만들어졌으므로 그대로 정본화하지 않는다. 어떤 상태가 구간 실패·강제 귀환·승무원 손실을 만드는지는 §6 미결 `2`에서 다시 정한다.

## 6. 새로 결정해야 하는 것

도킹을 지웠다고 해서 빈자리를 임의의 이름으로 바꾸지 않는다. 아래는 사용자·기획이 새로 확정해야 한다.

1. **정비 여력 획득 규칙.** 구간 생존, 선택한 위험, 남은 함선 상태, 사건 목표 중 무엇을 보상 입력으로 삼는가.
2. **구간 종료·실패 조건.** 고정 시간 생존, 사건 해결, 항로 진행, 강제 귀환 중 어떤 조합인가.
3. **구간 결과 UI.** 배에 새로 남은 손상·소모 자원·획득 자재·저장 상태 중 무엇을 우선해서 보여주는가.
4. **장기 항해 진척 표현.** 성계 지도, 목표 지점까지 남은 거리, 사건 완료 수 중 무엇을 주 진행으로 읽히게 하는가.
5. **레거시 판정 이름의 교체 순서.** 기획 용어 확정 뒤 코드·테스트·HUD·결과 화면을 한 카드에서 함께 바꿀 것인가.

이 다섯 답이 나오기 전에는 `DockProgress`를 `TravelProgress`로 기계적으로 이름만 바꾸지 않는다. 이름만 바꾸면 도킹 게이지가 항해 게이지라는 새 이름으로 그대로 남아, 이번 정정의 목적을 달성하지 못한다.

## 7. 수용 기준

> 게임 소개를 읽은 사람이 The Last Ship의 목표를 “5분 안에 도킹한다”가 아니라 **“한 척의 함선을 키우고 보존하며 장기 항해를 이어간다”**고 설명하면 진행 구조 정정 PASS.

> 구간 하나를 마친 뒤 팀이 결과 점수보다 **무엇을 고치고 어디에 다음 방을 붙일지** 먼저 이야기하면 함선 확장 축 PASS.

> 저장 후 다음 접속에서 같은 배치·자원·손상 맥락을 보고 별도 설명 없이 다음 결정을 이어가면 세이브 축 PASS.
