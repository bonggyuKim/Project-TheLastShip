> 상위 정본: `docs/content-loop-spec-ct01.md`(어휘·HUD 규칙) · `docs/game-feel-loop-review-v1.md` §3.1 `G-1`(c)(프리셋 순환)

## 1. 결론 먼저

프리셋 `3`종의 플레이어용 이름을 **`엔진 과열` · `전력 상실` · `선체 파손`** 으로 확정한다. 표기는 **결과 화면의 `다음 판` 줄 하나뿐**이고, 방금 끝난 판의 이름은 적지 않는다.

| enum | 플레이어용 이름 | `t=0` 근거값 | 첫 지배 문제 |
|---|---|---|---|
| `HighHeatHighThrust` | **엔진 과열** | `EngineHeat 0.94` · `ThrustDemand 0.92` | 냉각실 (`S-H1`) |
| `PowerOverloadLooseBattery` | **전력 상실** | `BusPower 0.63` · 배터리 미장착 | 전력실 (`S-P1`→`S-P2`) |
| `BadAttitudeHighOxygen` | **선체 파손** | `HullIntegrity 0.48` · 자세 `72°` · `ExistingDamage 0.42` | 산소실 + 조종석 (동시) |

이름 규칙은 **`[부위·계통 2음절] + [사고 2음절]`** 하나다. 셋 다 `4`음절이라 `다음 판` 줄에서 길이가 흔들리지 않고, 새 계통 용어를 하나도 만들지 않는다.

## 2. 이 규칙이 피해야 했던 충돌 3가지

이름을 짓는 일이 아니라 **이미 화면에 있는 어휘와 안 부딪히는 자리를 찾는 일**이었다. 후보를 세 번 버렸다.

### (가) 상황(`S-xx`) 이름과 겹치면 안 된다

처음 후보는 화면 문장을 그대로 줄인 `열 폭주` · `전력 끊김` · `자세 상실`이었다. `LastShiftSituations.cs:307`의 원인 `1`행(`엔진 열이 폭주하고 있다` · `배전이 끊겼다` · `배가 자세를 잃었다`)에서 온 것이라 새 용어가 `0`개라는 장점이 있었지만, **`S-H2`의 이름이 이미 `열 폭주`다**(`LastShiftSituations.cs:14`).

> 플레이어가 겪는 것: `열 폭주` 판을 시작한 지 `40`초, 열이 아직 `0.86`이라 `S-H2`는 안 켜졌다. 옆 사람이 "열 폭주 왔어?"라고 묻는다. **판 이름을 물은 건지 지금 상황을 물은 건지 아무도 모른다.**

프리셋은 판 전체를 부르는 이름이고 상황은 그 안에서 켜졌다 꺼지는 것이라, 두 층이 같은 단어를 쓰면 이 문장이 매 판 나온다. **프리셋 이름은 상황 이름과 단어를 공유하지 않는다** — 이것이 v1이 고정하는 첫 규칙이다.

### (나) 판정 `5`종과 문법이 겹치면 안 된다

`전력 부족`도 후보였으나 판정에 이미 `추력 부족`이 있다(`game-feel-loop-review-v1.md` §3.1-(a)). 결과 화면에서는 이 둘이 세로로 `320px` 안에 같이 뜬다.

```
추력 부족                     ← 64px 판정
...
다음 판 — 전력 부족           ← 24px
```

같은 `○○ 부족` 문법이 한 화면에 두 번 나오면 큰 줄이 판정인지 예고인지 한 박자 늦게 갈린다. **`부족`·`도킹`·`생환`·`질식`·`표류`는 판정 전용어이므로 프리셋 이름에 쓰지 않는다.**

### (다) 부품 이름을 쓰면 다음 판의 답을 미리 준다

`배터리 이탈`은 이름만으로 정확하지만 **첫 판에서 찾아내는 재미를 예고 줄이 먼저 소비한다.** 프리셋 이름은 계통까지만 말하고 부품(`냉각통`·`배터리`·`패치 플레이트`)은 말하지 않는다. 이건 `CT-01` §3.1이 HUD 지배 문제 `1`행에 건 제약("어느 계통인지까지만")을 예고 줄에도 그대로 적용한 것이다.

## 3. 이름별 근거

### 엔진 과열 — `HighHeatHighThrust`

열 `0.94`는 세 프리셋 중 유일하게 시작부터 위기 등급이고, 이 판의 모든 판단(냉각을 고치러 갈 것인가, 추력을 낮춰 버틸 것인가)이 열 하나에서 나온다. `엔진`을 앞에 둔 것은 화면에 `엔진 보호 잠금`이 이미 있어서 플레이어가 `엔진`을 열 계통의 이름으로 이미 읽고 있기 때문이다.

- **`과열`과 `폭주`를 구분해 쓴다.** `과열`은 판 이름, `폭주`는 `S-H2`. `ship-elements-and-situations-v1.md:56` 표가 `S-H1`을 `과열 경고`로 부른 곳이 한 군데 있는데, 그건 문서 내부 별칭이고 화면 문자열이 아니다(코드 `CauseLine`은 `냉각 결합부가 빠졌다`). 화면에서 두 단어가 만나지 않으므로 그대로 둔다

### 전력 상실 — `PowerOverloadLooseBattery`

`정전`을 안 쓴 이유가 이 이름의 핵심이다. `t=0`의 `BusPower`는 `0.63`이라 아직 배전이 끊긴 상태가 아니고(`S-P3` `배전이 끊겼다`는 연쇄 끝에 온다), **이 판의 정체는 "지금 정전"이 아니라 "전력을 잃어가는 중"이다.** `상실`은 그 진행형을 담으면서 `S-P1`~`S-P3` 어느 상황 이름과도 겹치지 않는다.

- 이 판만 결과가 산소 쪽으로 끝난다(전력 → 재가압 정지 → 산소, `ship-elements-and-situations-v1.md:1099`). 이름을 산소로 잡으면 `선체 파손` 판과 구분이 안 되므로 **시작 계통으로 부른다** — 세 이름 모두 같은 기준(시작)이라 규칙이 하나다

### 선체 파손 — `BadAttitudeHighOxygen`

**이 프리셋만 첫 지배 문제가 둘이다**(자세 `72°`로 `S-T1`, 선체 `0.48`로 `S-O1`이 `t=0`에 동시 활성 — `ship-elements-and-situations-v1.md:1104`). 그래서 `자세 이상`이나 `산소 파공` 어느 쪽으로 이름을 잡아도 판의 반쪽만 부른다.

`선체 파손`은 그 둘의 공통 뿌리다. 선체 `0.48`·누적 파손율 `0.42`가 세 프리셋 중 최악이고, 자세가 무너진 것도 파공이 난 것도 같은 충격의 결과다. 이름 하나로 두 축을 다 덮는 유일한 후보였다.

- **트레이드오프:** `선체`는 플레이어가 직접 조작하는 계통이 아니라서(고칠 수 있는 것은 파공·자세지 선체 자체가 아니다) 다른 두 이름보다 한 겹 추상적이다. 대신 이름이 거짓이 되지 않는다 — 자세만 부르면 산소로 죽은 판에서, 파공만 부르면 정렬 실패로 진 판에서 이름이 어긋난다

## 4. 표기 규칙

### 4.1 어디에 쓰는가

**결과 화면 `다음 판` 줄 하나뿐이다.** 아트 문서 §4 좌표표의 `440, 646, 1040, 34` · `24px` · `#9FB4CC` 줄을 그대로 쓰고, 레이아웃은 바뀌지 않는다.

```
다음 판 — 전력 상실 · [Space]
```

| 화면 | 프리셋 이름 표기 | 근거 |
|---|---|---|
| 결과 화면 `다음 판` 줄 | **한다** | 이 카드가 여는 자리 |
| 결과 화면 판정부(칩·큰 줄) | **안 한다** | §4.2 |
| 인게임 HUD | **안 한다** | 판 중에는 이름이 할 일이 없다. 지배 문제 `1`행이 이미 지금 상태를 말한다 |
| `F3` 디버그 층 | **안 한다** | enum 이름(`HighHeatHighThrust`)을 유지한다. QA는 코드 심볼로 말해야 로그와 붙는다 |

### 4.2 방금 끝난 판의 이름은 적지 않는다

칩 옆에 `선체 파손 — 표류`처럼 현재 판 이름을 넣는 안을 검토했고 채택하지 않았다.

1. **방금 겪은 판이라 이름이 필요 없다.** 이름의 기능은 예고(다음 판이 다른 사고임을 알리는 것)와 호칭(플레이어끼리 부르는 것)인데, 끝난 판은 둘 다 해당이 없다
2. 아트 문서 §4가 고정한 좌표표를 건드려야 한다 — 칩 `440, 286`과 판정 큰 줄 `440, 326` 사이에는 `40px`뿐이라 한 줄이 더 들어가면 위계 `3`단이 `4`단이 된다
3. 판정 큰 줄(`64px`)이 화면에서 가장 강한데, 그 위에 `선체 파손`이 붙으면 **진 이유가 판 이름 때문인 것처럼 읽힌다.** 실제로는 같은 프리셋에서 `5`종 판정이 다 나올 수 있다

**미결로 남기지 않고 v1에서 닫는다.** 다시 열려면 근거는 "플레이어가 지난 판을 이름으로 못 부른다"여야 하는데, 프리셋이 `3`개 고정 순환이라 그 상황이 잘 오지 않는다.

### 4.3 순환 순서

`엔진 과열` → `전력 상실` → `선체 파손` → (다시 `엔진 과열`). `LastShiftPreset` enum 순서와 같다.

축이 `1`개(열) → `1`개가 연쇄로 번짐(전력→산소) → `2`개 동시(자세+파공)로 늘어나는 순서이고, 협동 요구도 같은 방향으로 커진다(`선체 파손`이 `2`인 협동을 가장 강하게 요구 — `ship-elements-and-situations-v1.md:1104`). enum 순서를 그대로 쓰므로 tech에 새 상수가 필요 없다.

- **첫 판은 `엔진 과열`로 시작한다.** 지금 부트스트랩도 `HighHeatHighThrust`다(`LastShiftNetworkSandbox.cs:43`) — 바꾸지 않는다

### 4.4 tech 인계

`LastShiftSituationText`(`LastShiftSituations.cs`) 옆자리에 매핑 하나를 더한다. 새 상태 없음, 분기 하나다.

```csharp
public static string PresetDisplayName(LastShiftPreset preset) => preset switch
{
    LastShiftPreset.HighHeatHighThrust => "엔진 과열",
    LastShiftPreset.PowerOverloadLooseBattery => "전력 상실",
    _ => "선체 파손"
};
```

- 이름 문자열은 **플레이어 화면 전용**이다. 로그·`F3`·테스트 실패 메시지는 enum 이름을 계속 쓴다
- `다음 판` 줄은 아트 문서 §7 타임라인의 `0.80s`부터 입력을 받는다 — 이름이 붙어도 그 타이밍은 그대로다

## 5. 트레이드오프

- **`3`판이면 이름을 다 본다.** 프리셋이 `3`개뿐이라 이름의 예고 기능은 네 번째 판부터 사라지고, 그 뒤로는 호칭 기능만 남는다. 이건 프리셋을 늘리기 전까지는 해결되지 않으며, 이름이 없는 것보다는 낫다는 판단이다
- **이름이 난이도를 말하지 않는다.** `선체 파손`이 가장 어렵다는 것은 이름에서 안 읽힌다. 난이도 표기는 일부러 넣지 않았다 — 판정이 `5`종이라 "어려운 판에서 절충 생환"이 "쉬운 판에서 정상 도킹"보다 나은지 자체가 아직 안 정해졌고, 난이도 딱지를 먼저 붙이면 그 답을 미리 고정해 버린다
- **`4`음절 고정은 한글 기준이다.** 영문 로컬라이즈가 붙으면 `Hull Breach`(`11`자)까지 늘어나 `다음 판` 줄 폭 계산이 달라진다. 지금은 한글만 있으므로 `1040px` 안에서 문제가 없다

## 6. 미결

1. **자세 `72°`가 화면에서 안 보인다.** `ShipAttitudeDegrees`는 `F3` 문자열과 시뮬레이션에만 있고 배가 실제로 기울지 않는다(`LastShiftSandboxController.cs:1744`). `선체 파손` 판을 시작한 플레이어가 눈으로 확인할 수 있는 것은 산소 칸과 지배 문제 `1`행뿐이다 — 이름 문제가 아니라 연출 부채이고, `game-tech-director`/`game-art` 소관으로 넘긴다
2. **시작 화면·로비가 생기면 같은 이름을 쓴다.** 지금 결과 화면에만 두는 것은 그 화면이 없기 때문이고, 생기면 판 선택에도 이 `3`개를 그대로 쓴다. 새 이름을 만들지 않는다
3. **영문 표기 미정.** 로컬라이즈 계획이 잡힐 때 같이 정한다
