# AI 활용을 위한 게임 개발 구조화

> **핵심 주장**  
> AI가 게임 개발을 자동으로 구조화하는 것이 아니라, AI를 제대로 활용하기 위해 게임 개발을 먼저 구조화한다.

> **문서 목적**  
> PDF 제작 전에 내용·논리·표현을 검토하기 위한 Notion 원본 초안이다.  
> 이 문서가 확정된 뒤에만 시각 디자인과 PDF 레이아웃을 다시 만든다.

---

## 1. 한 문장 요약

사람의 창작 의도를 PM이 작업 단위로 구조화하고, `Discord Bot`으로 요청과 승인을 연결하며, `AgentDesk`의 카드·역할·격리된 작업 공간을 거쳐 `Planning`·`Tech`·`Art` 역할로 전달하고, 자동 검증·독립 QA·AnchorMind 기억으로 결과를 다음 작업까지 이어가는 AI 게임 개발 구조다.

## 2. 왜 이런 구조가 필요한가

AI는 코드를 만들고 문장을 쓰는 속도는 빠르지만, 다음 네 가지를 스스로 안정적으로 보장하지는 못한다.

| 개발 중 생기는 문제 | 구조적 대응 | 필요한 이유 |
| --- | --- | --- |
| 요청이 모호하다 | PM | 목표, 범위, 완료 조건을 먼저 고정한다. |
| 큰 작업이 서로 충돌한다 | 역할 분리와 격리된 작업 공간 | 코드·아트·씬·테스트의 책임과 변경 경계를 나눈다. |
| 세션이 바뀌면 맥락이 끊긴다 | AnchorMind | 결정·오류·절차를 다음 역할이 회상하도록 만든다. |
| AI의 완료 선언을 믿기 어렵다 | 증거·QA·인간 승인 | 컴파일·테스트·플레이 결과를 분리해서 확인한다. |

### 핵심 설계 원칙

`의도 → 범위 → 역할 → 증거 → 승인 → 기억`

AI를 한 명의 자율적인 개발자로 가정하지 않고, 명확한 경계와 검증 가능한 인수인계를 따라 일하는 역할 집합으로 사용한다.

## 3. 전체 개발 흐름

```text
사람의 의도
    ↓
Discord Bot
    ↓
PM의 목표·범위·완료 조건 구조화
    ↓
AgentDesk의 카드·역할·격리된 작업 공간
    ↓
Planning / Tech / Art 역할의 구현
    ↓
컴파일·테스트·정량 검증·독립 QA
    ↓
사람의 실제 플레이와 최종 승인
    ↓
AnchorMind에 결정·오류·절차 저장
    ↺ 다음 작업에서 회상
```

이 흐름의 핵심은 “AI가 무엇을 만들었는가”가 아니라 “사람의 의도가 어떤 단계와 증거를 거쳐 실제 게임 변경으로 변환됐는가”를 추적할 수 있다는 점이다.

## 4. 구성 요소별 역할

| 구성 요소 | 해결하는 문제 | 맡는 역할 | 남기는 결과 |
| --- | --- | --- | --- |
| 사람 | 재미, 방향, 우선순위는 자동화하기 어렵다 | 목표·플레이 감각·최종 승인 결정 | 요청, 피드백, 승인 |
| Discord Bot | 자연어 요청이 개발 흐름과 분리된다 | 요청 접수, 상태 알림, 승인 연결 | 대화 기록, 상태 변화 |
| PM | 큰 요청은 AI가 안정적으로 처리하기 어렵다 | 목표·의존성·수용 기준을 카드로 구조화 | 계획 카드, 우선순위, 완료 조건 |
| AgentDesk | 여러 역할이 같은 범위를 건드리면 충돌한다 | 담당 역할, 작업 공간, 칸반 상태 관리 | 담당자, worktree, 상태, 리뷰 |
| Planning | 카드의 목표를 플레이 흐름·규칙·UX와 구현 순서로 구체화 | 실행 계획, 의존성, 설계 기준 | 계획 문서, 기준 |
| Tech | 코드 변경은 실제 동작 증명이 필요하다 | 구현, 기술 판단, 컴파일·테스트 수행 | 코드 diff, 로그, 테스트 결과 |
| Art | 아트 결과는 엔진 적용과 품질 확인이 필요하다 | 자산 생성·적용·시각 품질 확인 | 원본, 교환 파일, 적용 결과 |
| Reviewer / QA | 구현자가 스스로 완료를 선언하면 편향이 생긴다 | 독립 관점에서 수용 기준과 증거 재검토 | PASS/FAIL, 반려 사유 |
| AnchorMind | 세션 사이에서 결정과 실패가 사라진다 | 작업 기억과 개발 기억의 저장·회상·공유 | 결정, 오류, 절차, 인수인계 |

## 5. PM: AI를 활용하기 위한 첫 번째 구조화

PM은 단순한 작업 관리자나 할 일 목록 작성자가 아니다. 사람의 의도를 목표·범위·완료 조건이 있는 카드로 바꾸고, AgentDesk가 적절한 역할과 작업 공간으로 전달할 수 있게 만드는 시작점이다.

### PM 카드에 들어가는 항목

- 플레이어에게 보이는 목표
- 변경 허용 범위와 변경하지 않을 범위
- 선행 작업과 후속 작업
- 컴파일·테스트·플레이 수용 기준
- 담당 역할과 검토 역할
- 결과 커밋, 로그, 문서 링크
- 예상 토큰 예산, 현재 사용량, 남은 예산, 컨텍스트 요약 시점

### PM을 먼저 두는 이유

1. AI가 필요 이상으로 범위를 넓히는 것을 막는다.
2. 한 카드 안에 구현과 검증을 같이 넣어 완료 조건을 명확하게 만든다.
3. 여러 역할이 같은 기준을 보고 작업할 수 있게 한다.
4. 작업이 중단되어도 다음 역할이 카드만 보고 이어받을 수 있다.

### 프롬프트 설계 방식

프롬프트는 “게임을 만들어줘”처럼 큰 요청 하나로 작성하지 않았다. 공통 골격을 유지하고, AgentDesk가 배정한 역할에 따라 해야 할 일과 증거를 다르게 지정했다.

```text
[역할]
이번 작업에서 너는 PM / Planning / Tech / Art / QA 중 어떤 역할인가?

[목표]
플레이어에게 어떤 변화가 보여야 하는가?

[현재 문맥]
관련 카드, 기존 결정, 현재 상태, 선행 작업은 무엇인가?

[허용 범위와 금지 범위]
이번 카드에서 바꿔도 되는 파일·씬·자산과 바꾸면 안 되는 범위는 무엇인가?

[완료 조건]
어떤 상태가 되면 작업을 완료했다고 판단하는가?

[검증 증거]
어떤 compile·test·정량 검산·실제 플레이 결과를 남겨야 하는가?

[보고 형식]
변경 파일, 실행한 명령, 결과, 남은 위험, 다음 역할에 넘길 내용을 어떤 순서로 보고할 것인가?
```

### 역할별 프롬프트 차이

- **PM**: 요청을 목표·범위·의존성·완료 조건이 있는 카드로 구조화하고, AgentDesk에 전달할 우선순위와 담당 역할을 정한다.
- **Planning**: PM 카드의 목표를 플레이 흐름·규칙·UX·상태 전이·구현 순서로 구체화한다. 새 기능을 임의로 추가하지 않는다.
- **Tech**: 지정된 worktree와 범위 안에서 구현하고, compile·대상 테스트·필요한 정량 검증과 raw evidence를 남긴다.
- **Art**: 자산의 규격·적용 경로·임포트 조건·시각 품질 기준을 확인하고, 원본과 엔진 적용 결과를 함께 전달한다.
- **Reviewer / QA**: 구현자의 설명을 그대로 믿지 않고 수용 기준을 독립적으로 재현해 PASS/FAIL과 근거를 기록한다.

### 이런 프롬프트를 사용한 이유

1. 범위와 금지사항을 명시해 AI의 과도한 변경과 스코프 확장을 막는다.
2. 완료 조건과 검증 증거를 함께 요구해 자연어 완료 선언을 줄인다.
3. 보고 형식을 고정해 다음 역할이 같은 문맥으로 이어받게 한다.
4. 역할별 프롬프트를 분리해 PM의 판단, Tech의 구현, Art의 품질, QA의 검증이 섞이지 않게 한다.

## 6. AgentDesk: 역할과 변경 경계를 관리하는 층

AgentDesk는 AI에게 일을 시키는 채널이 아니라, AI가 일할 수 있는 조건을 관리하는 작업 공간이다.

### 역할 분리

| 역할 | 주된 질문 |
| --- | --- |
| PM | 무엇을, 어디까지, 어떤 순서로 나눌 것인가? |
| Planning | 목표를 플레이 흐름·규칙·구현 순서로 어떻게 구체화할 것인가? |
| Tech | 실제로 어떻게 구현하고 동작을 증명할 것인가? |
| Art | 어떤 자산이 필요하고 엔진에서 어떻게 보여야 하는가? |
| Reviewer / QA | 완료 조건과 증거가 독립적으로 성립하는가? |

### 에이전트 간 대화와 자율 협업

에이전트들은 각자 고립되어 순서대로 결과만 내는 것이 아니라, AgentDesk가 만든 카드와 작업 공간 안에서 서로의 결과를 읽고 필요한 질문을 주고받으며 작업을 이어간다. 다만 대화가 자유로운 잡담으로 흘러가지 않도록 모든 메시지는 카드의 목표·범위·완료 조건과 연결된다.

1. **Planning → Tech / Art**: 플레이 흐름, 규칙, 상태 전이, 구현 순서와 필요한 자산 조건을 전달한다.
2. **Tech / Art → Planning**: 구현 중 발견한 제약, 누락된 규칙, 자산 적용 문제를 카드 스레드에 질문한다.
3. **Planning ↔ Tech ↔ Art**: 서로의 산출물을 확인하고 의존성이 바뀌면 작업 순서와 계약을 갱신한다.
4. **Reviewer / QA → 담당 역할**: 수용 기준을 재현한 뒤 실패 증거와 수정 범위를 돌려보낸다.
5. **PM / AgentDesk**: 범위 변경, 우선순위 충돌, 역할 재배정이 필요한 경우에만 개입해 카드를 다시 구조화한다.

여기서 ‘자율’은 에이전트가 승인 없이 범위를 넓힌다는 뜻이 아니다. 카드에 정의된 범위 안에서 다음 역할에게 질문하고, 결과를 전달하고, 필요한 재작업을 요청하는 협업 루프를 사람의 재지시 없이 수행한다는 의미다. 모든 대화와 산출물은 카드에 기록되고, 최종 범위 변경과 실제 플레이 품질 판단은 사람과 PM의 승인 아래 남는다.

```text
Planning의 실행 계획
        ↓ 질문·조건 전달
Tech / Art의 구현·자산 결과
        ↕ 제약·누락·적용 문제 피드백
Reviewer / QA의 독립 검증
        ↓ 실패 증거와 수정 범위
담당 역할의 재작업 → 재검토
```

### 칸반 상태

`BACKLOG → PLANNING → READY → DOING → REVIEW → DONE`

`REVIEW → DOING`은 실패가 아니라 보완을 위한 정상적인 되돌림이다.  
상태를 분리하면 “작업 중”, “검증 중”, “사람의 판단 대기”를 구분할 수 있다.

칸반은 각 카드의 **현재 상태와 책임**을 관리한다.

- 카드에는 목표·범위·완료 조건·담당 역할·격리된 worktree·검증 증거를 함께 둔다.
- 상태는 역할이 바뀌거나 검증 관문을 통과했을 때만 이동시켜, 작업 중인 카드와 승인 대기 카드를 구분한다.
- 카드 스레드에는 에이전트 간 질문, 결과, 실패 증거, 다음 행동을 남긴다.
- 같은 저장소와 같은 역할에 무거운 카드를 과도하게 병렬 배정하지 않도록 WIP와 작업 공간을 관리한다.

### 타임라인: 순서와 의존성 추적

칸반이 “지금 어디에 있는가”를 보여준다면, 타임라인은 “무엇이 먼저 끝나야 다음 작업이 시작되는가”를 보여준다.

- PM 카드 생성, Planning 완료, Tech·Art 착수와 완료, QA, 인간 승인 같은 마일스톤을 시간 순서로 기록한다.
- 독립적인 Tech·Art 작업은 병렬로 배치하고, Planning 결과나 공통 자산처럼 선행 조건이 있는 작업은 의존성이 풀린 뒤 시작한다.
- 시작·종료·대기·재작업·인수인계 시점을 기록해 카드의 lead time, 실제 작업 구간, 리뷰 대기 구간을 분리한다.
- 타임라인은 일정표가 아니라 병목과 충돌을 발견하는 관측 도구다. 측정하지 않은 인간 개입 시간이나 실제 API 비용을 시간 절감률로 추정하지 않는다.

```text
요청 접수 ─ PM 카드 ─ Planning ─┬─ Tech ─┐
                              └─ Art ──┴─ QA ─ 승인
```

### 토큰 관리: 컨텍스트와 비용의 운영 한계

토큰 관리는 단순히 사용 비용을 줄이는 기능이 아니라, 한 에이전트의 긴 세션이 오래된 로그와 불필요한 문맥으로 오염되지 않도록 하는 운영 장치다.

- PM 카드에 예상 토큰 예산·현재 사용량·남은 예산·다음 요약 시점을 기록한다.
- 프롬프트에는 현재 카드에 필요한 문맥만 넣고, 장기 결정·오류·절차는 AnchorMind에서 필요한 만큼만 회상한다.
- 예산 경고선에 도달하면 검증된 사실·변경 파일·남은 위험·다음 행동을 요약해 카드와 AnchorMind에 저장하고, 다음 역할에 인수인계한다.
- 예산 한도에 도달하면 새로운 범위를 추가하지 않고 현재 증거를 보존한 뒤, 같은 카드의 새 세션에서 이어간다.
- Discord Bot과 AgentDesk는 토큰 경고, 요약, 인수인계, 세션 재개를 카드 상태와 함께 알린다.

```text
칸반     = 현재 상태·책임
타임라인 = 순서·의존성·경과 시간
토큰     = 컨텍스트·사용량·인수인계 한도
```

실제 모델·API 사용량은 provider가 제공하는 원시 사용량이 있을 때만 비용으로 환산한다. 현재 기록에 없는 비용이나 인간 개입 시간을 임의로 만들어 성과 지표로 사용하지 않는다.

## 7. Discord Bot: 대화를 추적 가능한 작업으로 바꾸는 역할

사람은 자연어로 요청하지만, 개발 시스템은 구조화된 상태와 증거를 필요로 한다. Discord Bot은 이 둘 사이의 인터페이스다.

### 요청 변환 예시

1. 사람: “새 기능 개발을 시작해줘.”
2. Discord Bot: 요청을 PM에게 전달
3. PM: 목표·범위·완료 조건을 카드로 구조화
4. AgentDesk: 카드·역할·격리된 작업 공간을 만들고 Planning·Tech·Art에 배정
5. Reviewer / QA: 결과와 증거를 검토
6. 사람: 실제 플레이 후 승인 또는 수정 지시
7. Discord Bot: 상태와 다음 작업을 알리고 결정·절차를 AnchorMind에 공유

### Discord Bot을 사용하는 이유

- 요청·진행·리뷰·승인을 같은 대화 흐름에 남길 수 있다.
- 사람은 새로운 시스템 문법을 배우지 않고 자연어로 시작할 수 있다.
- 카드와 상태가 바뀔 때 담당자와 다음 행동을 알릴 수 있다.
- 승인 전후의 맥락을 나중에 다시 추적할 수 있다.

## 8. 증거와 인간 승인

AI 활용 구조의 종료 조건은 “완료했습니다”라는 문장이 아니라 변경·검증·판정의 흔적이다.

### 검증 루프

`변경 → 자동 검증 → 독립 QA → 인간 승인`

| 질문 | 남기는 증거 | 판단 주체 |
| --- | --- | --- |
| 변경이 의도한 범위인가? | 카드, 완료 조건, Git diff | Planning · Human |
| 구현이 실제로 동작하는가? | compile, EditMode/PlayMode, raw evidence | Tech · QA |
| 게임으로서 괜찮은가? | 실제 플레이, 시각 검토, 방향 피드백 | Human |
| 다음 작업이 안전한가? | 결정·오류·절차의 기억 기록 | AnchorMind |

### 자동화와 인간 판단의 경계

| 자동화에 맡기는 것 | 사람이 최종 판단하는 것 |
| --- | --- |
| 컴파일 오류와 예외 | 조작감, 가독성, 긴장감, 재미 |
| 상태 전이와 경계값 | 애니메이션의 생동감과 캐릭터성 |
| 좌표, 충돌, 네트워크 권한 | 화면 구도와 플레이 맥락 |
| EditMode·PlayMode 회귀 | 기능 우선순위와 제출 여부 |

자동 테스트 PASS는 기술적 조건을 만족했다는 뜻이지, 게임이 재미있다는 뜻은 아니다. 그래서 실제 플레이와 인간 승인을 별도의 관문으로 둔다.

## 9. AnchorMind: 같은 기준으로 이어서 일하기 위한 기억

AnchorMind는 한 가지 종류의 메모장이 아니라, 작업 문맥과 개발 지식을 나누어 저장하는 공용 기억 계층이다.

### 두 종류의 기억

| 기억 | 저장하는 것 | 사용하는 시점 |
| --- | --- | --- |
| 작업 기억·단기 | 현재 카드의 목표, 상태, 남은 문제, 다음 역할에 넘길 내용 | 작업 시작·중단·인수인계 |
| 개발 기억·장기 | 확정된 결정, 팀 규칙, 해결한 오류, 재사용 절차 | 새로운 작업을 시작할 때 |

### 기억이 이어지는 순서

`회상 → 작업 → 저장 → 공유`

1. 작업 전에 관련 결정과 절차를 회상한다.
2. 현재 코드와 실행 상태를 기억과 대조한다.
3. 확인된 결과와 해결 절차만 저장한다.
4. 다음 역할이 같은 기억을 이어받는다.

### 안전 원칙

- 기억은 현재 저장소와 실행 상태보다 우선하지 않는다.
- 비밀번호, 토큰, 인증 헤더, 개인정보는 저장하지 않는다.
- 추측과 쉽게 재생성되는 출력은 장기기억으로 남기지 않는다.

## 10. 기획 문서와 코드 관리

AI가 만든 결과를 바로 완료로 취급하지 않기 위해, 기획 문서와 코드의 정본을 분리하면서 카드·커밋·검증 증거로 연결한다.

### 기획 문서 관리

기획 문서는 무엇을 만들지, 왜 필요한지, 어떤 조건으로 완료로 볼지를 고정한다. 정확한 코드 구조나 좌표·구현 방법을 기획 문서에 몰아넣지 않고, PM 승인 후 별도 카드로 구현을 지시한다.

- **정본 내용**: 플레이 목표, 규칙, 플레이 흐름, 수용 기준, 의존성, 미결 질문
- **버전 관리**: 문서 버전, 변경 날짜, 변경 이유, 결정 주체, 폐기된 결정도 기록
- **범위 경계**: 기획은 의도·규칙·판정 기준을 정의하고, Tech·Art는 그 제약 안에서 구현 방법을 선택한다.
- **카드 연결**: 모든 구현 카드는 관련 문서와 섹션을 가리키고, 구현 결과는 커밋·테스트·로그·QA 결과를 다시 문서와 카드에 연결한다.
- **변경 절차**: 사람/PM의 결정 → 문서 갱신 → 카드 생성·수정 → 구현 → 검증 → 승인 → 결과와 다음 결정 기록
- Tech·Art가 기획과 충돌하는 제약을 발견하면 조용히 기획을 바꾸지 않고 카드 스레드에 보고해 PM과 사람이 판단한다.

### 코드 관리와 변경 출처

코드는 카드 단위로 격리하고, 변경이 어디서 왜 들어왔는지 추적할 수 있게 관리한다.

- 가능하면 카드별 branch와 worktree에서 작업해 역할 간 동시 수정 충돌과 공유 저장소의 위험을 줄인다.
- 한 커밋에는 하나의 논리적 기능·수정 범위와 필요한 테스트·문서 갱신을 묶고, 커밋과 카드 ID·변경 파일·검증 결과를 연결한다.
- 커밋 수 자체를 품질 점수로 보지 않는다. 중요한 것은 카드·수용 기준·diff·테스트·QA 증거가 서로 일치하는가이다.
- Tech는 compile, 대상 테스트, 회귀 테스트, 정량 검산과 raw evidence를 남긴 뒤 결과를 보고한다.
- QA와 PM은 변경 diff와 수용 기준을 독립적으로 검토한 뒤 통합 또는 재작업을 결정한다.
- 작업이 중단되면 대화 기록을 처음부터 재구성하지 않고 카드·worktree·커밋·AnchorMind 기억으로 이어간다.
- 같은 저장소를 쓰는 무거운 카드는 자원 충돌·cold cache·컨텍스트 비용을 고려해 병렬 수를 제한한다.

```text
기획 문서(무엇·왜·수용 기준)
        ↓ PM 카드
격리된 worktree(어떻게 구현할 것인가)
        ↓ commit + test + raw evidence
QA / 사람 승인
        ↓
문서·카드에 결과와 후속 결정 연결
```

## 11. 실제 작업에 적용한 사례

### UI 변경

- 아트 자산을 만들고 UGUI에 연결한다.
- 코드와 프리팹의 연결 상태를 확인한다.
- 회귀 테스트를 실행한다.
- 실제 플레이에서 가독성과 배치를 사람이 판단한다.

**왜 구조화했는가?**  
UI는 아트 파일만 바꾸거나 코드만 바꾸면 끝나지 않는다. 자산·UGUI 연결·테스트·실제 플레이가 하나의 완료 조건으로 묶여야 한다.

### 씬·배치 변경

- 기획 도안을 기준으로 배치 규칙을 정의한다.
- 기술 에이전트가 씬과 검산 도구를 재빌드한다.
- 겹침, 연결성, 이동 거리 같은 수치를 검산한다.
- 시각적 밀도와 플레이 감각은 사람이 검토한다.

**왜 구조화했는가?**  
좋아 보이는 배치를 감각만으로 판단하지 않고, 반복 실행 가능한 수치와 실제 플레이를 함께 사용하기 위해서다.

### 네트워크 작업

- 현재 범위의 host-client 동작을 먼저 고정한다.
- owner-authoritative 상태와 권한 경계를 검증한다.
- 후속 Relay/Lobby 작업은 별도 범위로 분리한다.
- LAN 테스트와 실제 플레이를 통해 연결 흐름을 확인한다.

**왜 구조화했는가?**  
네트워크 기능을 한 번에 확장하면 권한, 연결, 로비, 플레이 문제가 섞인다. 현재 완료 기준과 후속 범위를 분리해야 안전하게 진행할 수 있다.

## 12. 핵심 차별점

이 구조의 차별점은 AI가 코드나 에셋을 생성했다는 사실이 아니다.

1. AI를 Planning·Tech·Art·Review 역할로 나누고 서로 다른 완료 기준을 부여한다.
2. 자연어 요청을 카드·담당·상태·증거로 변환한다.
3. 역할별 작업 공간으로 변경 충돌과 책임을 분리한다.
4. 컴파일·테스트·정량 검증·실제 플레이를 한 흐름으로 연결한다.
5. 결정·오류·절차를 기억해 다음 작업의 출발점으로 재사용한다.

결국 사람은 방향과 품질을 통제하고, AI는 구조화된 범위 안에서 구현과 반복 검증을 수행한다.
